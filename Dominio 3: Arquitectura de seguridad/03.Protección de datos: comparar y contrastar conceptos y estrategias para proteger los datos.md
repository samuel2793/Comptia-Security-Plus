# 3.3 — Protección de datos: comparar y contrastar conceptos y estrategias

## Objetivo del examen

Debes poder identificar qué datos deben protegerse, en qué estado se encuentran, quién es responsable de ellos y qué estrategia resulta adecuada. La respuesta correcta depende del impacto de una divulgación, modificación, pérdida o indisponibilidad; no existe una única técnica que cubra todos los riesgos.

La **protección de datos** es el conjunto de prácticas, procesos y controles que preserva la confidencialidad, integridad y disponibilidad de la información durante todo su ciclo de vida: creación, recopilación, clasificación, uso, compartición, almacenamiento, retención y destrucción.

> Principio guía: primero se conoce y clasifica el dato; después se aplican controles proporcionales a su valor, sensibilidad, regulación y uso.

## 1. Clasificación de datos

La clasificación asigna una etiqueta según el valor del dato para la organización y el impacto que tendría una divulgación no autorizada. El **propietario del dato** define la clasificación y los requisitos de protección; no la decide automáticamente el administrador de sistemas.

Clasificar bien permite dedicar más controles a los datos de mayor riesgo y evitar tanto la infraprotección como la sobreclasificación. Si todo se etiqueta como «crítico», se encarecen y entorpecen los procesos, y la etiqueta deja de comunicar prioridad real.

### Esquema comercial típico

Los nombres y el número de niveles cambian entre organizaciones. Un ejemplo habitual, de menor a mayor sensibilidad, es:

| Clasificación | Ejemplos | Impacto si se divulga | Controles habituales |
|---|---|---|---|
| **Público** | Material aprobado para web, comunicados | Bajo o nulo | Integridad, control de publicación y copias de seguridad |
| **Interno / sensible** | Procedimientos internos, planes no publicados | Bajo a moderado | Acceso para personal autorizado, etiquetado y compartición controlada |
| **Privado** | Datos de empleados, nóminas, información operativa | Moderado o alto | Privilegio mínimo, cifrado, auditoría y retención definida |
| **Confidencial / restringido** | Código fuente, secretos comerciales, contratos delicados | Alto | Acceso muy limitado, cifrado fuerte, DLP, monitorización y acuerdos de confidencialidad |
| **Crítico** | Claves maestras, datos de pago, información esencial para continuidad | Muy alto | Controles reforzados, segregación, MFA, gestión de claves, monitorización continua y recuperación probada |

«Sensible», «privado», «confidencial» y «restringido» no tienen una jerarquía universal. En un escenario de examen, la pista decisiva es el daño causado por la exposición y la política de la organización, no el nombre aislado.

### Esquemas gubernamentales

Las entidades públicas pueden emplear etiquetas como no clasificado, confidencial, secreto o alto secreto, con reglas de acceso y manejo propias. No conviene mezclar automáticamente este esquema con el comercial: las definiciones, el impacto y la autoridad que etiqueta pueden ser distintos.

### Ciclo de vida y retención

Los requisitos de clasificación acompañan al dato durante su vida útil. Una política debe definir:

1. Qué datos se recogen y con qué finalidad.
2. Quién puede clasificarlos, consultarlos, modificarlos y compartirlos.
3. Dónde pueden almacenarse y procesarse.
4. Cuánto tiempo deben conservarse por necesidad operativa, contrato o requisito aplicable.
5. Cómo se eliminan, destruyen o anonimizan al terminar la retención.

Retener datos «por si acaso» incrementa superficie de ataque, coste y alcance de un incidente. A la vez, eliminar información sujeta a conservación obligatoria puede generar un problema legal u operativo. La política de retención debe revisarse con los responsables de negocio, privacidad y cumplimiento.

## 2. Roles y responsabilidad sobre los datos

Una protección eficaz distingue responsabilidades; el proveedor que aloja datos no decide necesariamente quién puede usarlos.

| Rol | Responsabilidad principal |
|---|---|
| **Data owner / propietario** | Decide clasificación, finalidad, requisitos de protección y quién puede acceder |
| **Data custodian / custodio** | Aplica controles técnicos y operativos: backups, almacenamiento, permisos y recuperación |
| **Data steward / gestor de datos** | Mantiene calidad, definiciones, metadatos y uso coherente del dato |
| **Data controller / responsable del tratamiento** | Determina fines y medios del tratamiento de datos personales, cuando aplica este marco |
| **Data processor / encargado del tratamiento** | Procesa datos por cuenta del responsable y según instrucciones/contrato |
| **Usuario** | Usa los datos únicamente conforme a la autorización y política recibida |

Los términos legales dependen de la jurisdicción y del contrato. Para un escenario, separa la decisión de negocio sobre el dato (owner/controller) de la operación técnica que lo protege (custodian/processor).

## 3. Estados de los datos

Los tres estados principales exponen amenazas diferentes. El mismo registro puede estar cifrado en una base de datos, viajar por una API y finalmente aparecer descifrado en memoria para que una aplicación lo procese.

| Estado | Qué significa | Riesgos frecuentes | Controles prioritarios |
|---|---|---|---|
| **En reposo (at rest)** | Almacenado en disco, base de datos, backup, snapshot o medio extraíble | Robo de soporte, acceso no autorizado, backup expuesto, remanencia | Cifrado, control de acceso, gestión de claves, backup seguro, borrado/destrucción segura |
| **En tránsito (in transit / in motion)** | Se mueve entre hosts, redes, servicios o ubicaciones | Interceptación, manipulación, suplantación, replay | TLS, VPN/IPsec cuando corresponde, autenticación mutua, validación de certificados y segmentación |
| **En uso (in use)** | Se crea, lee, modifica, procesa o mantiene en memoria | Robo de sesión, malware, privilegios excesivos, dumping de memoria | Privilegio mínimo, controles de aplicación, aislamiento, protección de endpoint, registros y entornos de ejecución protegidos |

El cifrado de disco es excelente frente a pérdida física de un portátil apagado, pero no protege de la misma forma a un atacante que ya controla la sesión de un usuario autorizado. Para datos en uso se necesitan controles de identidad, proceso y entorno además de cifrado.

### Granularidad del cifrado en reposo

| Nivel | Protege | Ventaja | Coste o limitación |
|---|---|---|---|
| Disco completo | Todo el dispositivo | Transparente y útil ante pérdida o robo de soporte | Con el sistema desbloqueado, la aplicación autorizada ve el contenido |
| Partición o volumen | Una parte o contenedor de almacenamiento | Separa grupos de datos y puede combinarse con cifrado de disco | Requiere definir bien qué datos quedan dentro |
| Archivo o carpeta | Objetos concretos | Granularidad para compartir o proteger documentos específicos | Mayor gestión por usuario/aplicación |
| Base de datos | Datos administrados por el motor | Protege ficheros de base de datos y backups según implementación | No sustituye permisos dentro de la base |
| Campo, columna o registro | Atributos concretos, como identificadores o pagos | Minimiza exposición de los atributos más sensibles | Más complejidad de aplicación, búsqueda y claves |

La clave importa tanto como el cifrado: separa claves de datos, aplica acceso mínimo, rotación, backup y revocación. Perder una clave puede hacer irrecuperable la información; exponerla anula gran parte de la protección.

## 4. Tipos de datos y riesgo

La clasificación indica el impacto para la organización; el **tipo de dato** describe su naturaleza y puede imponer obligaciones adicionales.

| Tipo | Ejemplos | Estrategias habituales |
|---|---|---|
| Datos regulados | Datos personales, salud, pagos | Minimización, control de acceso, cifrado, trazabilidad, retención y requisitos sectoriales aplicables |
| **PII** | Nombre, identificadores, dirección, datos que identifican o ayudan a identificar a una persona | Limitar recopilación y acceso; proteger combinación de atributos, no solo un campo aislado |
| Datos de salud / PHI | Historial, diagnósticos, tratamientos o pagos sanitarios asociados a una persona | Acceso por función, auditoría reforzada y controles acordes al marco aplicable |
| Secretos comerciales | Fórmulas, procesos, listas de clientes, estrategia | Segmentación, necesidad de conocer, DLP y acuerdos de confidencialidad |
| Propiedad intelectual | Código, diseños, obras, patentes, marcas | Gestión de acceso, repositorios protegidos, control de exportación y registro de cambios |
| Información legal | Contratos, litigios, asesoramiento legal | Restricción estricta, retención controlada y preservación cuando exista obligación de conservar |
| Información financiera | Facturas, cuentas, previsiones, transacciones | Separación de funciones, integridad, auditoría, prevención de fraude y protección de pagos |

La información legible por personas —documentos, hojas de cálculo o correo— sigue necesitando controles. También los requieren los datos no legibles directamente por personas, como binarios, bases de datos, telemetría, logs, snapshots y archivos de configuración: pueden contener secretos, tokens o información operativa.

## 5. Soberanía, residencia y localización de datos

La **soberanía de datos** alude a que los datos están sujetos a las leyes y autoridades de las jurisdicciones relevantes. La **residencia de datos** se refiere a dónde se almacenan físicamente. También importan los lugares de procesamiento, soporte, replicación, backup, recuperación y acceso administrativo.

En servicios cloud, «elegir una región» no resuelve por sí solo todos los requisitos. Hay que conocer el flujo completo de los datos y las condiciones contractuales del proveedor. Las obligaciones concretas dependen del tipo de datos, las personas afectadas, el contexto de tratamiento y las jurisdicciones implicadas; deben revisarse con especialistas de cumplimiento y asesoría legal.

Controles y preguntas útiles:

- Mantener inventario y mapa de ubicación, flujos, copias y subencargados.
- Seleccionar regiones y servicios que cumplan los requisitos de residencia cuando aplique.
- Controlar transferencias transfronterizas y accesos de soporte administrativo.
- Definir cifrado, gestión de claves y retención coherentes en regiones primarias y de recuperación.
- Verificar cómo se eliminan datos y backups al finalizar un contrato o migrar de proveedor.

### Restricciones geográficas

El geofencing puede permitir o bloquear accesos según señales geográficas, como dirección IP, región de dispositivo o red corporativa. Reduce exposición de inicios de sesión anómalos, pero una IP no demuestra por sí sola identidad ni ubicación real: puede cambiar, usar VPN o ser compartida.

Debe complementar MFA, evaluación de riesgo, gestión de dispositivos y autorización por recurso. Bloquear países enteros sin analizar necesidades legítimas de negocio, viajes y soporte puede provocar indisponibilidad o falsas detecciones.

## 6. Técnicas de protección: qué problema resuelve cada una

### Comparación esencial

| Técnica | ¿Se puede recuperar el original? | Propósito principal | Ejemplo de uso |
|---|---|---|---|
| **Cifrado** | Sí, con la clave correcta | Confidencialidad | Disco, backup, base de datos, API o archivo compartido |
| **Hashing** | No; es una función unidireccional | Integridad y verificación; almacenamiento de contraseñas | Comparar un archivo o verificar una contraseña mediante hash lento y salado |
| **Enmascaramiento** | Depende del diseño; normalmente se oculta el valor mostrado | Reducir exposición visual o en entornos no productivos | Mostrar `**** 1234` en lugar del número completo |
| **Tokenización** | Sí, consultando el sistema que mantiene la relación token-valor | Reducir exposición del dato sensible en sistemas consumidores | Un token sustituye un número de tarjeta en una aplicación de cobros |
| **Ofuscación** | No es una garantía criptográfica; dificulta comprensión | Reducir legibilidad o ingeniería inversa | Ocultar nombres o estructura de código/datos |
| **Segmentación** | No transforma el dato | Contener accesos y movimiento lateral | Separar datos de pago de una red de usuarios |
| **Restricción de permisos** | No transforma el dato | Limitar quién puede leer, cambiar, copiar o borrar | RBAC/ABAC, ACL y necesidad de conocer |

### Cifrado

El cifrado transforma texto claro en texto cifrado usando un algoritmo y una clave. Protege confidencialidad, pero no decide quién puede acceder ni verifica por sí solo que la aplicación use el dato correctamente. Acompáñalo de gestión de claves, control de acceso, integridad autenticada y copias de seguridad de las claves cuando corresponda.

### Hashing

Un hash genera una salida de longitud fija para verificar que un dato no ha cambiado. No se «desencripta» un hash. Para contraseñas se usan funciones de derivación diseñadas para este fin, con sal única y parámetros de coste; un hash rápido sin sal no es suficiente para proteger credenciales.

### Enmascaramiento, anonimización y tokenización

El **enmascaramiento** oculta parte o todo el valor presentado; puede ser dinámico —cada usuario ve según su rol— o estático para generar datos de prueba. Si la transformación conserva la posibilidad de identificar a una persona mediante otras fuentes, no debe suponerse que elimina obligaciones de privacidad.

La **tokenización** sustituye un valor sensible por un token sin valor útil fuera del sistema de tokenización. El almacén que relaciona token y dato original es crítico y necesita controles reforzados. Es habitual cuando varios sistemas necesitan referirse al mismo dato sin almacenar el valor original.

La **ofuscación** dificulta interpretar un dato o código, pero no debe presentarse como sustituto de cifrado, control de acceso o autorización.

### Segmentación y permisos

La segmentación separa redes, bases de datos, cuentas cloud o dominios de seguridad para limitar el alcance de una intrusión. Los permisos implementan el principio de **necesidad de conocer** y **privilegio mínimo** mediante ACL, RBAC, ABAC u otros modelos.

Revisa accesos periódicamente, separa funciones incompatibles y revoca privilegios cuando cambia el puesto, se completa un proyecto o termina la relación laboral. El acceso de solo lectura también puede producir una brecha de confidencialidad.

## 7. Prevención de pérdida de datos (DLP)

**DLP** combina personas, procesos y tecnología para identificar y evitar que datos sensibles salgan o se expongan de forma no autorizada, por error o de manera maliciosa. DLP no sustituye clasificación ni control de acceso: se apoya en ellos para saber qué debe vigilar.

Un sistema DLP puede detectar patrones —por ejemplo, identificadores de pago—, etiquetas de clasificación, huellas de documentos, reglas de contexto o modelos de contenido. Según la política, puede alertar, bloquear, poner en cuarentena, cifrar o requerir justificación.

| Ámbito | Qué puede vigilar |
|---|---|
| Endpoint | Copia a USB, impresión, captura, subida desde aplicaciones locales |
| Red | Correo, web, transferencia de archivos y otros canales salientes visibles |
| Cloud / SaaS | Comparticiones públicas, colaboración externa, almacenamiento y descargas |

Una regla DLP demasiado amplia bloquea trabajo legítimo; una muy permisiva deja escapar información. Empieza en modo de monitorización cuando sea apropiado, ajusta falsos positivos, define excepciones aprobadas y conserva registros útiles para investigación.

## 8. Selección de estrategia por escenario

| Escenario | Respuesta inicial más apropiada |
|---|---|
| Portátil perdido con información de empleados | Cifrado de disco, MFA/gestión del dispositivo, borrado remoto y evaluación de exposición de claves |
| Un analista necesita usar datos reales para pruebas | Enmascaramiento o tokenización; evitar copias innecesarias de producción |
| Aplicación de pagos necesita guardar referencias sin números de tarjeta | Tokenización y protección reforzada del almacén de tokens |
| Se debe verificar que un archivo descargado no fue alterado | Hash o firma/verificación de integridad, no cifrado como único control |
| Usuarios remotos acceden a archivos confidenciales | TLS/VPN o ZTNA, MFA, autorización mínima, logs y controles de endpoint |
| Información altamente sensible en varias redes | Segmentación, cifrado, permisos por función y supervisión de accesos |
| Datos sujetos a requisitos de ubicación | Mapa de flujos, residencia/procesamiento/backup revisados y controles contractuales/técnicos |
| Riesgo de enviar documentos confidenciales por correo | Clasificación, DLP, cifrado cuando corresponda y formación al usuario |

## Errores frecuentes

- Confundir clasificación con tipo de dato: «PII» describe un tipo; «confidencial» expresa una clasificación según política.
- Pensar que cifrado de disco protege automáticamente datos en uso por una sesión comprometida.
- Decir que un hash se puede descifrar o usarlo como sustituto de cifrado.
- Tratar la ofuscación como cifrado fuerte.
- Aplicar seguridad de puerto o segmentación y olvidar que usuarios autorizados aún pueden exfiltrar datos.
- Guardar tokens y la tabla de correspondencia con los mismos controles débiles.
- Mirar solo la región principal cloud e ignorar backups, logs, replicación y soporte.
- Conservar todos los datos indefinidamente «por si acaso».

## Resumen

- La clasificación, la titularidad y la retención dan contexto a cualquier decisión de protección.
- Los datos en reposo, en tránsito y en uso requieren controles distintos y complementarios.
- Elige cifrado para confidencialidad recuperable, hashing para integridad/verificación, tokenización para sustituir valores sensibles y masking para ocultar visualizaciones o datos de prueba.
- Soberanía, residencia y transferencias exigen conocer el ciclo completo del dato, no solo dónde está la aplicación principal.
- DLP ayuda a detectar y prevenir exfiltración, pero funciona mejor con clasificación, permisos y procesos maduros.
