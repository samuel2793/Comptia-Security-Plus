# 4.2 Gestión de activos

## Objetivo del examen

Explicar las implicaciones de seguridad de una gestión adecuada de activos de hardware, software y datos.

Un activo desconocido no se puede proteger, parchear, supervisar ni retirar correctamente. La gestión de activos reduce vulnerabilidades porque permite saber **qué existe, quién es responsable, dónde está, qué datos trata, qué versión usa y cuándo debe retirarse**.

## Qué es un activo

Un activo es cualquier elemento que aporta valor a la organización o que debe protegerse. En seguridad se consideran especialmente:

| Categoría | Ejemplos |
|---|---|
| **Hardware** | Portátiles, servidores, switches, móviles, discos, sensores, impresoras y equipos OT. |
| **Software** | Sistemas operativos, aplicaciones, licencias, SaaS, firmware, imágenes y scripts. |
| **Datos** | Bases de datos, documentos, backups, registros, claves, propiedad intelectual y PII. |
| **Servicios e identidades** | Cuentas cloud, dominios, certificados, APIs, proveedores, cuentas de servicio y suscripciones. |

La gestión de activos recorre todo el ciclo de vida: planificación, adquisición, recepción, registro, despliegue, uso, mantenimiento, reasignación, retirada y disposición final.

## Implicaciones de seguridad

Una gestión deficiente de activos produce riesgos previsibles:

- Sistemas sin parchear porque no figuran en el inventario.
- Software no autorizado, licencias vencidas o dependencias sin soporte.
- Cuentas, claves, certificados, DNS o almacenamiento cloud abandonados.
- Datos sensibles almacenados en ubicaciones desconocidas o conservados demasiado tiempo.
- Equipos perdidos, robados, reutilizados o desechados con datos recuperables.
- Dificultad para contener incidentes, evaluar exposición o notificar a los afectados.

La gestión de activos es, por tanto, una base de la gestión de vulnerabilidades, del hardening, de la continuidad, de la respuesta a incidentes y del cumplimiento.

## Adquisición y aprovisionamiento

**Adquisición** es obtener un bien o servicio. **Procurement** o aprovisionamiento es el proceso más amplio: identifica la necesidad, evalúa opciones y proveedores, obtiene aprobaciones, compra, recibe e integra el activo.

Comprar una herramienta no es el final del proceso de seguridad; es el punto en que comienza su gestión.

### Controles antes de comprar

| Área de revisión | Preguntas de seguridad |
|---|---|
| Necesidad y riesgo | ¿Qué problema resuelve? ¿Qué datos y procesos afectará? |
| Proveedor | ¿Tiene prácticas de seguridad, soporte, avisos de vulnerabilidades y compromisos contractuales adecuados? |
| Compatibilidad | ¿Funciona con identidad, red, monitorización, backup y controles existentes? |
| Ciclo de vida | ¿Cuál es la fecha de fin de soporte? ¿Cómo se actualiza y cómo se retira? |
| Datos y privacidad | ¿Dónde almacena/procesa datos? ¿Qué subprocesadores intervienen? ¿Cómo exporta y elimina datos? |
| Licencias y costes | ¿Se pueden inventariar licencias, renovaciones y cuentas? ¿Hay costes de salida? |
| Seguridad técnica | ¿Soporta MFA, cifrado, registros, APIs seguras, RBAC y configuración centralizada? |

Para compras pequeñas pueden existir tarjetas corporativas o reembolsos; para activos relevantes se suele usar una **orden de compra (PO)** y un flujo de aprobación. La diferencia de pago no elimina la necesidad de revisión de seguridad: una aplicación SaaS adquirida sin evaluación puede introducir *shadow IT*, datos expuestos o identidades sin control.

### Recepción y alta del activo

Antes de entregar un activo a producción conviene:

1. Verificar que el producto recibido coincide con lo aprobado y procede de una fuente confiable.
2. Registrar identificador, propietario, ubicación, versión, fecha de compra, garantía, licencia y fecha de fin de soporte.
3. Aplicar una línea base segura, parches, cifrado y agentes de gestión o protección necesarios.
4. Asignar responsable técnico y propietario de negocio/datos cuando corresponda.
5. Documentar dependencias, procedimientos de soporte y planes de recuperación.

## Inventario, asignación y seguimiento

El inventario es la fuente de verdad de los activos autorizados. Debe conciliarse con la realidad mediante descubrimiento técnico, registros de compras, escaneos autenticados, MDM, herramientas de gestión de endpoints, plataformas cloud y comprobaciones físicas.

| Dato de inventario | Por qué importa |
|---|---|
| Identificador, serie o etiqueta | Relaciona el activo físico o lógico con los registros. |
| Tipo, fabricante, modelo y versión | Permite identificar vulnerabilidades y compatibilidad. |
| Ubicación, red o cuenta cloud | Delimita impacto, exposición y responsabilidad. |
| Usuario asignado y propietario | Facilita soporte, rendición de cuentas y retirada. |
| Clasificación y criticidad | Determina controles, prioridad de parcheo y recuperación. |
| Estado de parcheado y configuración | Revela activos vulnerables o fuera de línea base. |
| Fecha de compra, garantía y fin de soporte | Permite planificar renovación o retirada. |

### Monitorización, tracking y enumeración

- **Monitorización de activos:** mantiene el inventario con estado, versión, asignación y cumplimiento.
- **Tracking:** sigue ubicación, movimiento, condición o custodia de activos físicos mediante etiquetas, MDM, GPS cuando sea apropiado o sistemas de inventario.
- **Enumeración:** descubre e identifica activos, servicios, sistemas operativos y software presentes en una red o entorno.

La enumeración recurrente permite detectar dispositivos no autorizados, software no gestionado, hosts olvidados y diferencias entre el inventario declarado y el observado. Todo hallazgo debe investigarse: no conviene dar por legítimo un activo únicamente porque responde en la red.

## Propiedad y roles de datos

La propiedad de datos no significa «quién creó un archivo». Describe responsabilidades sobre la clasificación, el uso, la protección y la calidad de la información. Las denominaciones exactas pueden variar según el marco legal y la organización.

| Rol | Responsabilidad principal |
|---|---|
| **Data owner / propietario de datos** | Define clasificación, valor, uso permitido, retención y controles requeridos desde la perspectiva de negocio. Suele pertenecer al área que conoce los datos. |
| **Data custodian / custodio** | Implementa y opera controles técnicos: almacenamiento, backups, acceso, cifrado, disponibilidad y recuperación. Suele ser TI u operaciones. |
| **Data steward** | Mantiene calidad, definiciones, metadatos, etiquetado y uso coherente de los datos. |
| **Data controller / responsable del tratamiento** | Decide fines y medios del tratamiento de datos personales, en los marcos donde se usa este término. |
| **Data processor / encargado del tratamiento** | Trata datos por cuenta e instrucciones del controlador. Puede ser un proveedor externo. |
| **Privacy officer / DPO u homólogo** | Supervisa privacidad, obligaciones, derechos de interesados, políticas y cumplimiento aplicable. |

TI conoce los sistemas, por lo que normalmente actúa como custodio, no como propietario de negocio de todos los datos. El área financiera, sanitaria, comercial o de producto es quien normalmente puede clasificar mejor los datos que genera y decidir qué necesidad de negocio justifica conservarlos.

### Clasificación y etiquetado

Cada activo y conjunto de datos debe clasificarse según valor, sensibilidad, criticidad e impacto de divulgación, alteración o pérdida. La etiqueta dirige decisiones como:

- Quién puede acceder y con qué autenticación.
- Dónde se puede almacenar o procesar.
- Si necesita cifrado, DLP, monitorización o controles de exportación.
- Prioridad de backup, recuperación, parcheo y sustitución.
- Tiempo de retención y método de disposición final.

Una clasificación excesiva puede encarecer y dificultar el uso legítimo; una clasificación insuficiente deja activos críticos sin protección. La meta es aplicar controles proporcionales al riesgo.

## Gestión de dispositivos móviles

Los móviles, tabletas, portátiles y wearables se desplazan fuera de las instalaciones, por lo que requieren inventario, asignación y controles de pérdida o robo.

Un **MDM** (*Mobile Device Management*) ayuda a registrar, configurar y supervisar dispositivos móviles. Según política y plataforma puede aplicar cifrado, bloqueo de pantalla, actualizaciones, perfiles Wi-Fi/VPN, aplicaciones aprobadas, detección de root/jailbreak, borrado remoto y separación de datos laborales.

| Escenario | Implicación de gestión de activos |
|---|---|
| Se pierde un móvil corporativo | Confirmar asignación, revocar sesiones y certificados, bloquear o borrar remotamente y registrar el incidente. |
| Un empleado abandona la organización | Recuperar activos, revocar accesos, eliminar datos corporativos y actualizar inventario/licencias. |
| BYOD | Definir consentimiento, nivel de gestión permitido, separación de datos, soporte y borrado selectivo. |
| Se adquieren cientos de móviles | Registrar serie, usuario, política, estado de cumplimiento y fecha de renovación desde el alta. |

El objetivo es proteger los datos corporativos sin ignorar la privacidad, propiedad y obligaciones de los usuarios, especialmente en BYOD.

## Gestión de software, licencias y activos cloud

El inventario no puede limitarse al hardware. Para software y cloud debe incluir aplicaciones instaladas, versiones, bibliotecas, licencias, propietarios, repositorios, cuentas, suscripciones, recursos desplegados, secretos y certificados.

Controles relevantes:

- Mantener una lista de software autorizado y bloquear o investigar aplicaciones no aprobadas.
- Conocer versiones y dependencias para priorizar vulnerabilidades y parches.
- Retirar licencias, cuentas y permisos que ya no se necesiten.
- Identificar activos cloud sin propietario, como buckets, IP públicas, snapshots, APIs, claves o proyectos olvidados.
- Supervisar fechas de renovación, caducidad de certificados y fin de soporte.
- Mantener una **SBOM** cuando corresponda para conocer componentes de software y dependencias.

Una cuenta cloud o una clave API sin propietario es un activo abandonado: puede acumular costes, contener datos o proporcionar acceso no autorizado aunque no exista un servidor físico asociado.

## Retirada y disposición de activos

La retirada (*decommissioning*) es la eliminación controlada de un activo de servicio. La disposición es su reutilización, devolución, venta, reciclaje o destrucción posterior. Ambas requieren planificación porque los datos, configuraciones, credenciales y dependencias pueden sobrevivir a la desconexión del activo.

### Lista de comprobación de retirada

1. Confirmar aprobación y que no quedan dependencias o requisitos de retención.
2. Hacer backup o archivar la información necesaria y validar que se puede recuperar.
3. Revocar credenciales, tokens, certificados, claves, reglas DNS, accesos de red y cuentas de servicio.
4. Eliminar el activo de balances, monitorización, backups, automatización, CMDB e inventario operativo.
5. Sanear o destruir el medio de almacenamiento según tipo de medio, sensibilidad y política.
6. Actualizar licencias, contratos, propiedad y documentación.
7. Conservar evidencia de la disposición y cerrar la cadena de custodia.

Retirar un servidor sin eliminar sus credenciales, DNS, cuentas de automatización o backups puede mantener una vía de acceso o costes ocultos. Retirar un software sin revisar dependencias puede interrumpir servicios críticos.

### Saneamiento de medios

**Saneamiento** significa aplicar un método que hace que los datos no sean recuperables con las técnicas previstas por la política. El método depende del soporte, su reutilización, la clasificación de la información y requisitos aplicables.

| Método | Cuándo resulta adecuado | Consideración importante |
|---|---|---|
| **Clear / borrado lógico controlado** | Reutilización interna de medios de bajo o medio riesgo, conforme a política. | Debe verificarse; un borrado normal de archivos no es saneamiento. |
| **Purge / purga** | Cuando se requiere mayor protección y el medio puede seguir siendo reutilizable. | El método debe ser compatible con el tipo de medio, especialmente SSD y almacenamiento moderno. |
| **Cryptographic erase** | El medio estaba cifrado correctamente y se pueden destruir de forma fiable todas las claves que permiten descifrarlo. | No es válido si hay copias de las claves o el cifrado no cubría los datos. |
| **Degaussing** | Medios magnéticos compatibles, como ciertas cintas o discos. | No sirve para SSD; normalmente inutiliza el medio. |
| **Destrucción física** | Datos muy sensibles, medios dañados o cuando no se permite reutilización. | Puede incluir trituración o desintegración mediante un proveedor autorizado. |

No existe un número mágico de sobrescrituras válido para todos los soportes. Las unidades SSD, la memoria flash y los sistemas de almacenamiento complejos pueden gestionar bloques internamente, de modo que se debe usar un procedimiento validado y apropiado al medio, no una técnica heredada aplicada a ciegas.

### Certificación y cadena de custodia

La organización debe conservar evidencia de que la disposición se realizó correctamente. Puede incluir identificador del activo, tipo de medio, método de saneamiento, fecha, responsable, proveedor, testigos, resultado de verificación y certificado de destrucción cuando corresponda.

Esto prueba cumplimiento, facilita auditorías y reduce la incertidumbre si un activo retirado aparece más tarde en un incidente o investigación.

## Retención de datos

La retención define qué información se conserva, durante cuánto tiempo, en qué ubicación y bajo qué controles. Debe equilibrar necesidad de negocio, obligaciones legales/regulatorias, investigación, derechos de privacidad, coste y riesgo.

| Decisión | Implicación de seguridad |
|---|---|
| Conservar datos demasiado tiempo | Aumenta superficie de ataque, coste, complejidad y posible impacto de una brecha. |
| Eliminar datos demasiado pronto | Puede incumplir obligaciones, impedir auditorías, investigaciones o recuperación operativa. |
| Retener sin clasificación | Dificulta aplicar controles proporcionales y cumplir requisitos de soberanía o privacidad. |
| Archivar correctamente | Conserva datos necesarios con controles, acceso y recuperación definidos. |

El ciclo de vida de los datos suele incluir creación o recopilación, uso, almacenamiento, intercambio, archivo y disposición. Una política útil especifica disparadores de retención, posibles *legal holds*, propietarios, ubicaciones de copias y procedimiento de eliminación verificable.

> Cuantos más datos se conservan, más datos deben protegerse. La minimización y la disposición oportuna reducen tanto riesgo como coste.

## Escenarios frecuentes de examen

| Situación | Concepto o acción probable |
|---|---|
| Se detecta un portátil no registrado en la red. | Enumeración, investigación de activo no autorizado y actualización del inventario. |
| Un jefe de finanzas decide la etiqueta y protección de balances. | Data owner. |
| Un administrador configura backups, ACL y cifrado según instrucciones del dueño. | Data custodian. |
| Un proveedor SaaS procesa datos personales por instrucciones de la empresa. | Data processor; la empresa puede ser data controller según el marco aplicable. |
| Un móvil corporativo desaparece. | MDM: localizar si está permitido, bloquear/borrar, revocar accesos y actualizar inventario. |
| Un SSD cifrado se reutilizará tras retirar un sistema. | Evaluar saneamiento compatible; cryptographic erase solo si la gestión de claves permite invalidar todos los datos. |
| Un disco con información altamente sensible no debe reutilizarse. | Destrucción física conforme a política y evidencia/certificación. |
| Se compra una aplicación cloud sin revisión de TI o seguridad. | Riesgo de shadow IT; aplicar proceso de procurement y alta de activo. |
| Un servidor se apaga definitivamente pero mantiene certificados y DNS. | Retirada incompleta; revocar accesos y eliminar dependencias antes de cerrar el activo. |

## Errores habituales

- Tener una hoja de inventario estática y no contrastarla con descubrimiento técnico.
- Registrar solo hardware e ignorar SaaS, licencias, cuentas cloud, certificados, claves y datos.
- Asignar la propiedad de todos los datos a TI en vez de al área que conoce su valor y finalidad.
- Confundir un archivo eliminado o un disco formateado con un medio saneado.
- Aplicar degaussing a SSD o asumir que la sobrescritura repetida funciona igual en todos los medios.
- Usar cryptographic erase sin confirmar que el cifrado y la destrucción de claves cubren todos los datos.
- Retirar un activo sin eliminar identidades, secretos, DNS, backups y automatizaciones relacionadas.
- Conservar datos indefinidamente «por si acaso» sin una política de retención.
- No documentar la cadena de custodia ni obtener evidencia del saneamiento o destrucción.

## Resumen para memorizar

- La gestión de activos responde: **qué existe, dónde está, quién responde por ello, qué datos trata y cuándo se retira**.
- El inventario y la enumeración permiten descubrir activos no autorizados y priorizar parches y vulnerabilidades.
- El **data owner** clasifica y define requisitos; el **custodian** implementa controles técnicos; el **steward** mantiene calidad y metadatos.
- Procurement seguro revisa proveedor, compatibilidad, ciclo de vida, datos, soporte y controles antes de la compra.
- MDM facilita inventario, configuración, parches, cumplimiento y borrado remoto de móviles.
- La retirada segura revoca accesos, gestiona dependencias, conserva datos necesarios y sanea o destruye medios.
- Clear, purge, crypto erase, degaussing y destrucción física no son intercambiables: el medio y la sensibilidad determinan el método.
- La retención debe ser justificable y limitada: más datos retenidos implican más datos que proteger.

8. ¿Qué aporta un certificado de destrucción o saneamiento?

### Respuestas

1. Porque identifica sistemas, versiones y propietarios para poder aplicar parches, configuraciones, controles y seguimiento.
2. El data owner del área de negocio correspondiente, por ejemplo el responsable financiero.
3. El data custodian.
4. La adquisición obtiene el bien o servicio; procurement cubre el proceso completo de necesidad, evaluación, aprobación, compra e integración.
5. Revocar credenciales y dependencias, gestionar backups/retención, sanear datos, actualizar inventario y documentar la disposición.
6. Porque el degaussing actúa sobre magnetismo y las SSD usan memoria flash, no medios magnéticos.
7. Cuando los datos estaban cifrados adecuadamente y se pueden destruir de forma fiable todas las claves de descifrado pertinentes.
8. Aporta evidencia auditable de que se siguió un método de disposición definido para un activo concreto.
9. Puede contener datos, secretos o exposición pública sin supervisión, además de generar costes y riesgo de acceso no autorizado.
10. Porque aumenta coste, complejidad, superficie de ataque e impacto potencial de una brecha, y puede contradecir obligaciones de minimización.
