# 4.1 Seguridad de recursos informáticos

## Objetivo del examen

Dado un escenario, aplicar técnicas de seguridad comunes a recursos informáticos. El objetivo consiste en identificar el activo, el riesgo y el control más adecuado: endpoint, dispositivo móvil, recurso cloud, red inalámbrica, aplicación, IoT, sistema embebido o entorno industrial.

La solución suele combinar controles preventivos, detectivos y correctivos. No basta con instalar una herramienta: hay que configurar, mantener y supervisar el recurso durante todo su ciclo de vida.

## Principios de aplicación de controles

| Principio | Aplicación práctica |
|---|---|
| **Mínimo privilegio** | Otorgar solo los permisos, servicios y accesos necesarios. |
| **Defensa en profundidad** | Combinar capas: identidad, red, endpoint, cifrado, monitorización y recuperación. |
| **Hardening** | Reducir la superficie de ataque eliminando configuraciones, cuentas y servicios innecesarios. |
| **Segmentación** | Limitar qué recursos pueden comunicarse entre sí y reducir el movimiento lateral. |
| **Configuración segura** | Usar una línea base aprobada y detectar desviaciones. |
| **Gestión continua** | Inventariar, parchear, registrar, revisar y retirar activos de forma segura. |

Una pregunta de escenario suele pedir el control que reduce directamente un riesgo concreto. Por ejemplo, si un dispositivo no puede actualizarse, la respuesta puede ser segmentación y controles compensatorios; si una aplicación recibe entradas no confiables, la respuesta es validación del lado del servidor y consultas parametrizadas.

## Despliegue y seguridad de dispositivos móviles

Los móviles, tabletas y wearables pueden contener credenciales, correo, archivos corporativos y datos sensibles. El modelo de propiedad determina cuánto control puede ejercer la organización y qué cuestiones de privacidad debe resolver.

| Modelo | Propiedad y elección | Ventajas | Riesgos o límites |
|---|---|---|---|
| **BYOD** (*Bring Your Own Device*) | El empleado usa su dispositivo personal. | Menor compra inicial; familiaridad para el usuario. | Menos control, diversidad de equipos, privacidad y riesgo de mezclar datos personales y corporativos. |
| **COPE** (*Corporate-Owned, Personally Enabled*) | La empresa es propietaria; se permite cierto uso personal. | Gran control, gestión y estandarización. | Coste de adquisición y necesidad de definir claramente privacidad y borrado. |
| **CYOD** (*Choose Your Own Device*) | La empresa ofrece un catálogo limitado de dispositivos aprobados. | Equilibrio entre elección y soporte estandarizado. | Coste corporativo y menor libertad que BYOD. |

No existe un modelo universalmente mejor. Se elige según sensibilidad de los datos, presupuesto, requisitos legales, capacidad de soporte, necesidad de control y experiencia del usuario.

### MDM y controles móviles

Un sistema de **MDM** (*Mobile Device Management*) permite administrar dispositivos móviles de manera centralizada. Dependiendo de la plataforma y de la política, puede:

- Exigir PIN o contraseña robusta, bloqueo automático y cifrado del dispositivo.
- Aplicar actualizaciones, configuraciones Wi-Fi/VPN y certificados.
- Detectar equipos rooteados o con *jailbreak* y negarles acceso corporativo.
- Restringir el sideloading, aplicaciones no aprobadas, almacenamiento externo o copias de datos.
- Separar datos y aplicaciones laborales mediante contenedores o perfiles de trabajo.
- Hacer borrado selectivo de datos corporativos o borrado total cuando proceda.
- Evaluar cumplimiento antes de conceder acceso mediante NAC o acceso condicional.

| Riesgo | Control apropiado |
|---|---|
| Aplicaciones desde fuentes no oficiales (**sideloading**) | Bloquear instalación no autorizada, permitir solo tiendas/aplicaciones aprobadas y aplicar MDM. |
| **Rooting** o **jailbreaking** | Detectar incumplimiento y bloquear o limitar el acceso corporativo. |
| Pérdida o robo de dispositivo | Cifrado, bloqueo, MFA, localización cuando sea permitida y borrado remoto. |
| Wi-Fi público o Bluetooth desconocido | VPN según la política, cifrado de aplicación, no emparejar con desconocidos y desactivar radios no necesarias. |
| Datos personales y laborales mezclados | Contenedor de trabajo, gestión de aplicaciones móviles y reglas de DLP. |

## Hardening de endpoints y servidores

**Hardening** es el proceso de reforzar un sistema mediante configuración segura, eliminación de funciones innecesarias y aplicación de controles adecuados. Se aplica a servidores, estaciones de trabajo, portátiles, dispositivos de red, móviles, máquinas virtuales y dispositivos especializados.

### Controles fundamentales

| Técnica | Propósito |
|---|---|
| Cambiar credenciales y parámetros por defecto | Evitar que se exploten valores conocidos de fábrica. |
| Deshabilitar puertos, protocolos y servicios innecesarios | Reducir superficie de ataque y consumo de recursos. |
| Gestión de parches | Corregir vulnerabilidades de sistema operativo, firmware, aplicaciones y controladores. |
| Firewall basado en host | Restringir tráfico entrante y saliente en el propio equipo. |
| EDR/antimalware | Detectar, investigar y responder a actividad maliciosa en endpoints. |
| Allowlisting de aplicaciones | Permitir la ejecución de software expresamente autorizado. |
| Cifrado | Proteger datos en reposo; proteger también claves de recuperación. |
| Control de acceso | Aplicar RBAC, mínimo privilegio y MFA en accesos administrativos. |
| Registro y auditoría | Facilitar detección, investigación y verificación de cumplimiento. |

Un sistema heredado o sin soporte no debe permanecer expuesto como si fuera un endpoint normal. Si no puede retirarse o actualizarse inmediatamente, se emplean controles compensatorios: segmentación estricta, listas de permitidos, filtrado de red, acceso administrativo controlado, supervisión intensiva y un plan de sustitución.

### Gestión de parches

La gestión de parches es un ciclo, no simplemente instalar actualizaciones:

1. Inventariar activos, software, firmware y versiones.
2. Priorizar según criticidad, exposición, explotación conocida e impacto de negocio.
3. Probar en un entorno representativo cuando el riesgo operativo lo requiera.
4. Desplegar de forma controlada, con ventana de mantenimiento y plan de reversión.
5. Verificar instalación, funcionalidad y ausencia de regresiones.
6. Documentar excepciones, controles compensatorios y fecha prevista de remediación.

Un parche puede ser urgente, pero en entornos críticos no se debe ignorar la compatibilidad ni la seguridad funcional. El control correcto es una gestión de cambios y parches basada en riesgo, no una actualización indiscriminada.

## Líneas base seguras

Una **línea base segura** es una configuración estándar aprobada que establece el nivel mínimo de seguridad esperado para un tipo de activo. Puede basarse en requisitos internos, recomendaciones del fabricante y marcos de seguridad aplicables.

### Ciclo de vida de una línea base

1. Identificar el activo, sus datos, funciones, amenazas y requisitos.
2. Crear una imagen, plantilla o configuración inicial endurecida.
3. Instalar únicamente aplicaciones, agentes y servicios requeridos para el rol.
4. Analizar vulnerabilidades y corregir desviaciones antes de aprobarla.
5. Versionar, documentar y desplegar la configuración de forma consistente.
6. Supervisar el cumplimiento y corregir el *configuration drift* o deriva de configuración.
7. Revisarla al cambiar amenazas, software, infraestructura o necesidades del negocio.

Las líneas base se pueden aplicar mediante imágenes, scripts, políticas de grupo, administración de configuración o infraestructura como código. La automatización mejora consistencia, pero los cambios en la línea base también necesitan pruebas, revisión y control de versiones.

### Políticas centralizadas

En entornos Windows, las **GPO** permiten aplicar de forma centralizada configuraciones como contraseñas, bloqueo de pantalla, permisos, auditoría y restricciones de software. En Linux, mecanismos como **SELinux** aplican controles de acceso obligatorio para limitar qué procesos y recursos puede utilizar cada dominio. El concepto evaluado es el mismo: imponer una configuración coherente y limitar el impacto de un proceso o usuario comprometido.

## Seguridad en nube y virtualización

En cloud se aplica un modelo de **responsabilidad compartida**. El proveedor suele proteger la infraestructura subyacente del servicio contratado; el cliente sigue siendo responsable, entre otras cosas, de identidades, permisos, datos, configuraciones, claves, cargas de trabajo y monitorización según el modelo de servicio.

### Controles para recursos cloud

- Aplicar MFA, roles con mínimo privilegio y cuentas administrativas separadas.
- Evitar credenciales permanentes; usar identidades de carga de trabajo y rotación de secretos.
- Cifrar datos en reposo y en tránsito; gestionar de forma segura las claves.
- Usar plantillas seguras para máquinas virtuales, contenedores y recursos cloud.
- Segmentar redes virtuales y limitar reglas de seguridad a origen, destino y puerto necesarios.
- Registrar actividad, cambios de configuración y accesos; alertar sobre configuraciones inseguras.
- Mantener parches de sistemas gestionados por el cliente y actualizar dependencias.
- Eliminar recursos, snapshots, claves y datos residuales según la política de retención.
- Diseñar redundancia y probar recuperación ante fallos, no asumir que la nube elimina todos los SPOF.

La multitenencia exige aislamiento robusto entre clientes. Para máquinas virtuales, esto incluye proteger el hipervisor, usar imágenes confiables, aplicar parches y segmentar redes. Un **VM escape** intenta salir de una máquina virtual para afectar al hipervisor o a otras cargas; por ello la plataforma y sus actualizaciones son especialmente sensibles.

En contenedores, no se debe tratar una imagen como confiable solo por estar disponible en un repositorio. Se usan imágenes mínimas, procedencia controlada, escaneo, ejecución sin privilegios, secretos fuera de la imagen y separación de redes y permisos.

## IoT, sistemas embebidos e industriales

### IoT

El **Internet of Things (IoT)** reúne dispositivos conectados con sensores, software y capacidad de comunicación: cámaras, medidores, wearables, electrodomésticos, sensores ambientales y equipos industriales. Un hub o sistema de control puede recopilar datos y enviar órdenes a varios dispositivos.

Riesgos comunes:

- Contraseñas por defecto y servicios expuestos innecesariamente.
- Firmware sin soporte o sin mecanismo de actualización seguro.
- Interfaces de administración inseguras y comunicaciones sin cifrar.
- Inventario incompleto de dispositivos y datos recopilados.
- Uso como punto de entrada para movimiento lateral hacia la red corporativa.

Controles principales:

- Cambiar credenciales predeterminadas y deshabilitar servicios no requeridos.
- Mantener firmware validado y aplicar actualizaciones de forma controlada.
- Segmentar IoT en una red o VLAN específica, con reglas mínimas hacia sistemas corporativos.
- Usar autenticación mutua, cifrado y gestión de identidad cuando el dispositivo lo soporte.
- Inventariar, monitorizar comportamiento y planificar reemplazo de dispositivos sin soporte.

### Sistemas embebidos y RTOS

Un **sistema embebido** es un componente informático dedicado a una función concreta dentro de un dispositivo mayor. Puede aparecer en automóviles, maquinaria, equipos médicos, robots, cámaras o electrodomésticos. Muchos emplean un **RTOS** (*Real-Time Operating System*), diseñado para ejecutar tareas con tiempos de respuesta predecibles.

En estos recursos, la disponibilidad y la seguridad física pueden ser tan importantes como la confidencialidad. El parcheado puede ser difícil por criticidad operacional, validación regulatoria, acceso físico o vida útil prolongada.

| Problema | Técnica de seguridad |
|---|---|
| Firmware modificado o no autorizado | Secure boot, firmware firmado y validación criptográfica antes de instalar o arrancar. |
| Sistema que no se puede parchear | Segmentación, listas de permitidos, filtrado estricto, monitorización y plan de reemplazo. |
| Comunicación por redes no confiables | Cifrado y túneles seguros, por ejemplo VPN/IPsec cuando sea apropiado. |
| Acceso físico no autorizado | Protección física, puertos bloqueados, inventario y control de mantenimiento. |

### ICS y SCADA

Los **ICS** (*Industrial Control Systems*) supervisan o controlan procesos físicos. **SCADA** es un tipo de sistema industrial utilizado para supervisar y controlar procesos distribuidos geográficamente, como agua, energía, transporte o tuberías. También existen PLC y DCS para automatización y control de procesos.

En OT/ICS, un cambio mal diseñado puede afectar seguridad física, producción o servicios esenciales. Por eso se priorizan evaluación de impacto, disponibilidad, pruebas controladas y coordinación entre operaciones, ingeniería y seguridad.

Controles habituales:

- Separar IT y OT mediante zonas, conductos, firewalls industriales y listas de comunicación explícitas.
- Limitar y registrar accesos remotos; usar MFA y bastiones cuando proceda.
- Inventariar activos y revisar configuraciones, firmware y dependencias.
- Aplicar parches solo tras análisis y pruebas compatibles con la operación.
- Supervisar protocolos y comportamientos anómalos sin interrumpir procesos críticos.
- Mantener respaldo de configuraciones, procedimientos de recuperación y controles físicos.

## Bluetooth y conectividad inalámbrica de corto alcance

Bluetooth facilita comunicación de corto alcance, pero puede ampliar la superficie de ataque si se deja activo, visible o sin actualizar.

| Riesgo | Mitigación |
|---|---|
| Emparejamiento inseguro | Emparejar solo dispositivos conocidos, comprobar identidad y usar métodos de autenticación apropiados. |
| Dispositivo falso o suplantado | No aceptar solicitudes inesperadas; validar el dispositivo antes de vincularlo. |
| Interceptación o manipulación | Usar cifrado y mantener dispositivos actualizados. |
| Exposición innecesaria | Desactivar Bluetooth cuando no sea necesario y usar modo no detectable salvo durante emparejamiento. |
| Vulnerabilidades de firmware | Aplicar actualizaciones del fabricante y retirar dispositivos sin soporte. |

Pistas de terminología: **bluejacking** suele referirse a mensajes no solicitados; **bluesnarfing**, a extracción no autorizada de datos; **bluebugging**, a control no autorizado de funciones; **bluesmacking**, a denegación de servicio; y **BlueBorne** identifica una familia histórica de vulnerabilidades Bluetooth. En un examen, reconoce principalmente el efecto y el control preventivo.

## Seguridad de infraestructura Wi-Fi

La seguridad Wi-Fi combina diseño físico, selección de protocolos, autenticación fuerte, segmentación y supervisión.

### Ubicación de puntos de acceso y estudios de sitio

Un **site survey** analiza cobertura, interferencias, capacidad, roaming, obstáculos y redes cercanas antes o durante el despliegue. Un **heat map** representa cobertura, intensidad de señal y utilización del espectro por zonas.

El objetivo no es maximizar la potencia indiscriminadamente. Una señal que se extiende fuera de las instalaciones aumenta exposición. Se ajustan ubicación, potencia, antenas, canales y número de AP para tener cobertura útil dentro de las áreas requeridas y reducir fugas de señal hacia el exterior.

En instalaciones grandes, varios AP pueden formar un **ESS** (*Extended Service Set*) para permitir roaming. La planificación de canales evita interferencia co-canal y de canales adyacentes; en 2,4 GHz normalmente se emplean los canales no solapados permitidos en la región, como 1, 6 y 11 donde sea aplicable.

### Configuraciones inalámbricas

| Tecnología | Uso de examen |
|---|---|
| **WEP** | Obsoleto e inseguro; no debe utilizarse. |
| **WPA/WPA con TKIP** | Legado y no recomendado. |
| **WPA2 con AES-CCMP** | Mejor que protocolos antiguos; puede ser necesario por compatibilidad. |
| **WPA3** | Opción preferible cuando equipos y requisitos lo permiten; mejora el intercambio de credenciales y la protección de tramas de gestión. |
| **OWE / Enhanced Open** | Aporta cifrado individual en redes abiertas compatibles, pero no reemplaza la autenticación de una red empresarial. |

Para acceso corporativo, suele ser adecuado **WPA-Enterprise con 802.1X**, EAP y un servidor AAA. Se autentica a usuarios o dispositivos individualmente, en vez de compartir una única contraseña Wi-Fi.

### AAA, RADIUS, TACACS+ y EAP

**AAA** significa autenticación, autorización y contabilidad (*accounting*): comprobar identidad, decidir qué puede hacer una identidad y registrar su actividad.

| Elemento | Función típica |
|---|---|
| **RADIUS** | AAA centralizado, muy usado para acceso de red, Wi-Fi empresarial y VPN. |
| **TACACS+** | AAA usado habitualmente para administración de dispositivos de red; permite control granular de comandos. |
| **EAP** | Marco extensible de autenticación; no es un único método de credenciales. |
| **PEAP, EAP-TLS, EAP-TTLS, EAP-FAST** | Métodos o familias EAP con diferentes mecanismos de túnel y certificados. Se eligen según infraestructura de identidad y requisitos. |

La seguridad depende de validar certificados, proteger credenciales, aplicar políticas por rol y segmentar invitados, IoT y usuarios corporativos. Ocultar el SSID no reemplaza cifrado ni autenticación fuerte.

## Seguridad de aplicaciones

La seguridad de aplicaciones busca prevenir, detectar y corregir vulnerabilidades en el código, la configuración, las dependencias y la ejecución de software.

### Validación de entradas

Toda entrada es no confiable: formularios, parámetros URL, APIs, cabeceras, archivos, cookies, mensajes entre servicios y datos de terceros. La validación debe realizarse **en el servidor**, aunque la validación en cliente mejora la experiencia de usuario.

Buenas prácticas:

- Definir listas de valores, tipos, longitud, formato y rango aceptados.
- Rechazar entradas inesperadas; preferir allowlists frente a bloquear casos conocidos.
- Usar consultas parametrizadas para bases de datos, en lugar de concatenar entradas en consultas.
- Codificar la salida según el contexto para prevenir XSS.
- Separar permisos, manejo de errores y registros de información sensible.

La validación de entrada ayuda a prevenir inyecciones, XSS, errores de formato y ciertos fallos de lógica, pero forma parte de una defensa en profundidad, no es el único control.

### Cookies seguras

Las cookies de sesión pueden ser robadas o utilizadas indebidamente si están mal configuradas. Para sesiones web, se aplican atributos como:

| Atributo o práctica | Protección |
|---|---|
| `Secure` | Envía la cookie solo mediante HTTPS. |
| `HttpOnly` | Impide el acceso de scripts del navegador a la cookie. |
| `SameSite` | Reduce el envío no deseado en contextos entre sitios y mitiga parte del riesgo CSRF. |
| Rotación de identificador de sesión | Reduce fijación de sesión; renovar tras autenticación o cambio de privilegios. |
| Caducidad y cierre de sesión | Limita cuánto tiempo puede reutilizarse una sesión comprometida. |

Los atributos de cookies complementan, pero no sustituyen, la protección CSRF, HTTPS, autenticación segura, autorización en servidor y prevención XSS.

### Análisis de código y pruebas

| Técnica | Cuándo se analiza | Qué aporta |
|---|---|---|
| **SAST** (*Static Application Security Testing*) | Sin ejecutar la aplicación: código fuente, bytecode o binarios. | Detecta patrones inseguros temprano en el ciclo de desarrollo. |
| **Revisión manual de código** | Lectura por pares o especialistas. | Aporta contexto de diseño y lógica que una herramienta puede no detectar. |
| **DAST** (*Dynamic Application Security Testing*) | Aplicación en ejecución desde el exterior. | Encuentra fallos observables en tiempo de ejecución y configuración. |
| **Fuzzing** | Aplicación en ejecución con entradas inesperadas o malformadas. | Busca fallos, excepciones, cuelgues y manejo inseguro de entradas. |
| **Stress testing** | Bajo carga extrema o condiciones exigentes. | Evalúa estabilidad, límites y comportamiento de recuperación. |

SAST y DAST no son sustitutos: uno observa el código sin ejecutarlo y el otro observa el comportamiento en ejecución. Juntos cubren clases de fallos diferentes.

### Firma de código y sandboxing

La **firma de código** usa una firma digital para verificar la procedencia y la integridad de software, scripts, actualizaciones o firmware. Confirma que el artefacto fue firmado por una identidad confiable y que no ha sido modificado desde la firma; no demuestra que el software esté libre de vulnerabilidades o malware si el firmante fue comprometido o actuó maliciosamente.

El **sandboxing** ejecuta código en un entorno aislado con permisos y recursos limitados. Puede usarse en navegadores, aplicaciones, análisis de malware, máquinas virtuales o contenedores. Limita el daño potencial, pero no elimina la necesidad de aplicar parches ni protege frente a todas las vulnerabilidades de escape del aislamiento.

## Selección rápida por escenario

| Escenario | Técnica más apropiada |
|---|---|
| Usuarios instalan aplicaciones no autorizadas en móviles corporativos. | MDM, allowlisting y bloqueo de sideloading. |
| Un móvil ha sido rooteado o tiene jailbreak. | Detectarlo con MDM y denegar o restringir acceso corporativo. |
| Un servidor conserva servicios y puertos que no usa. | Hardening: deshabilitar servicios y filtrar puertos no necesarios. |
| Se detectan configuraciones distintas en equipos del mismo rol. | Línea base segura, gestión de configuración y corrección de deriva. |
| Un dispositivo IoT vulnerable necesita seguir operativo. | Segmentación, filtrado estricto, monitorización y plan de reemplazo. |
| Una red Wi-Fi corporativa usa una contraseña compartida. | WPA-Enterprise/802.1X con EAP y RADIUS, si el escenario requiere identidad individual. |
| El Wi-Fi se detecta claramente fuera del edificio. | Site survey, heat map y ajuste de AP, potencia o antenas. |
| Una web procesa datos enviados por usuarios. | Validación de entradas del lado del servidor y consultas parametrizadas. |
| Se necesita verificar origen e integridad de un instalador. | Firma de código y validación de la cadena de confianza. |
| Se debe probar código sospechoso sin poner en peligro el host. | Sandbox aislado. |

## Errores frecuentes

- Considerar el MDM como control suficiente sin políticas, cifrado, identidad y monitorización.
- Creer que el cifrado de un dispositivo sustituye el borrado remoto, MFA o gestión de claves.
- Dejar servicios, cuentas o protocolos por defecto «por si acaso».
- Aplicar una línea base una sola vez y no vigilar desviaciones.
- Asumir que el proveedor cloud protege automáticamente permisos, datos y configuraciones del cliente.
- Conectar IoT u OT directamente a la red corporativa sin segmentación.
- Elegir WEP o WPA/TKIP por compatibilidad sin reconocer el riesgo heredado.
- Validar datos solo en el navegador y no en el servidor.
- Confundir firma de código con garantía de que una aplicación no tiene vulnerabilidades.
- Parchear sistemas industriales críticos sin evaluación de impacto, pruebas y coordinación operativa.

## Resumen para memorizar

- **BYOD** prioriza flexibilidad; **COPE** da más control corporativo; **CYOD** ofrece elección limitada y estandarizada.
- **MDM** aplica configuración, parches, cumplimiento y protección de datos móviles.
- **Hardening** reduce la superficie de ataque: cambiar valores por defecto, parchear, deshabilitar servicios, restringir software y aplicar mínimo privilegio.
- Una **línea base segura** es una configuración aprobada, versionada, desplegada y supervisada continuamente.
- En cloud, la seguridad es **compartida**: el cliente sigue protegiendo identidades, permisos, datos y configuraciones.
- IoT, sistemas embebidos e ICS requieren inventario, segmentación, firmware seguro, controles compensatorios y protección física.
- Para Wi-Fi empresarial, prioriza cifrado moderno, 802.1X/EAP, AAA y segmentación.
- **SAST** analiza código sin ejecutar; **DAST** analiza la aplicación en ejecución.
- La validación de entradas debe ocurrir en el servidor; la firma de código aporta procedencia e integridad; el sandboxing aporta aislamiento.
