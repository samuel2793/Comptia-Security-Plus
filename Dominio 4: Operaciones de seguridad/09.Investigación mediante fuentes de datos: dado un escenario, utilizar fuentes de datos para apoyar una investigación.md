# 4.9 Investigación mediante fuentes de datos

## Objetivo del examen

Dado un escenario, utilizar fuentes de datos para apoyar una investigación.

En este objetivo no basta con memorizar definiciones. Debes leer una alerta, un informe o un fragmento de registro, reconocer el patrón relevante, determinar si es benigno, sospechoso o malicioso, y seleccionar la siguiente acción más apropiada.

La investigación de incidentes consiste en reunir, analizar e interpretar evidencia para responder preguntas como estas:

- ¿Qué ocurrió?
- ¿Cuándo empezó y qué sistemas, cuentas o datos están afectados?
- ¿El evento fue bloqueado, tuvo éxito o aún se está produciendo?
- ¿Qué fuente adicional permitiría confirmarlo?
- ¿Qué medida de contención, erradicación o recuperación corresponde?

Un dato aislado rara vez demuestra por sí solo que ha ocurrido una intrusión. La confianza aumenta al correlacionar varias fuentes: por ejemplo, un pico de tráfico saliente en NetFlow, un proceso desconocido en EDR y una conexión a un dominio malicioso en DNS.

> Principio clave: una alerta inicia la investigación; la correlación de evidencias permite concluirla.

---

## Método para resolver escenarios de logs

Usa este proceso cada vez que recibas un extracto de datos en el examen:

1. **Identifica la fuente.** Determina si procede de un firewall, SIEM, EDR, IDS/IPS, aplicación, sistema operativo, captura de paquetes, escáner de vulnerabilidades o metadatos.
2. **Lee los campos importantes.** Hora, activo, usuario, IP de origen y destino, protocolo, puerto, acción, severidad, estado y detalle.
3. **Busca el patrón.** No te fijes únicamente en una línea: compara repeticiones, secuencias, tasas, destinos y cambios respecto a la línea base.
4. **Valora el resultado.** Diferencia entre intento bloqueado, evento detectado sin bloqueo, actividad confirmada y actividad normal.
5. **Correlaciona.** Busca la fuente que confirmaría o descartaría la hipótesis: autenticación, DNS, EDR, registros web, flujo de red, inventario o calendario de cambios.
6. **Prioriza por impacto real.** Un evento de gravedad alta que fue bloqueado puede requerir menos urgencia que una exfiltración detectada sin bloqueo.
7. **Elige una respuesta proporcionada.** Contener, preservar evidencia, verificar alcance, aplicar un parche, revocar credenciales o ajustar un control, según el escenario.

Antes de correlacionar, normaliza las horas. Los registros de distintas zonas horarias, o con relojes desincronizados, pueden construir una cronología falsa. UTC y la sincronización de tiempo son especialmente importantes.

## Mapa rápido de fuentes de investigación

| Fuente | Responde mejor a | Limitación principal |
|---|---|---|
| SIEM | Correlación centralizada, alertas y búsquedas entre fuentes | Depende de la calidad, cobertura y normalización de los datos recibidos |
| Dashboard | Tendencias, picos y prioridades iniciales | No sustituye el detalle de los eventos originales |
| Informe automatizado | Resumen operativo, hallazgos y acciones ya ejecutadas | Puede contener falsos positivos o requerir contexto |
| Escáner de vulnerabilidades | Exposición técnica y priorización de remediación | Una vulnerabilidad no demuestra explotación |
| NetFlow, sFlow e IPFIX | Quién habló con quién, volumen y duración de flujos | Generalmente no contienen la carga útil |
| PCAP | Cabeceras, flags y, si se capturó, contenido de paquetes | Mucho volumen; puede no existir captura del momento exacto |
| Firewall | Conexiones permitidas o bloqueadas por IP, puerto y protocolo | Un firewall de red no suele mostrar el contenido de la aplicación |
| WAF | Peticiones HTTP y patrones de ataque web | No corrige por sí solo el fallo de programación subyacente |
| Logs de aplicación | Acciones y errores dentro de una aplicación concreta | Su formato y nivel de detalle varían |
| EDR o endpoint | Procesos, archivos, cambios de registro y conexiones del equipo | Puede no estar instalado o bien configurado en todos los activos |
| Logs de autenticación del SO | Inicios de sesión, fallos, privilegios y bloqueos | Requieren contexto sobre la cuenta y la actividad esperada |
| IDS/IPS | Detección o prevención de firmas y anomalías de red | Una alerta necesita validación; el bloqueo depende de la configuración |
| Logs de red | Eventos de routers, switches, ARP, interfaces y protocolos | Pueden no contener identidad de usuario o contenido |
| Metadatos | Contexto de archivos, correo, llamadas u objetos | Describen datos; no necesariamente muestran su contenido |

## SIEM: consolidación, correlación y alertas

Un SIEM, Security Information and Event Management, centraliza eventos procedentes de aplicaciones, firewalls, endpoints, servidores, directorios, IDS/IPS y dispositivos de red. Permite buscar y relacionar datos casi en tiempo real.

Un sensor o agente es el componente que recoge datos en el endpoint o dispositivo y los envía al repositorio central. La cobertura importa: un SIEM no puede detectar lo que sus sensores no registran.

### Aspectos importantes de un SIEM

- **Sensibilidad:** cuánto y qué se registra. Más detalle ayuda a investigar, pero incrementa coste, ancho de banda, procesamiento, almacenamiento y ruido.
- **Alertas:** se generan al cumplirse condiciones, por ejemplo, cinco fallos de autenticación de una misma cuenta en pocos minutos.
- **Tendencias:** un aumento sostenido de fallos de inicio de sesión puede indicar fuerza bruta, una mala configuración o una aplicación con credenciales caducadas.
- **Correlación:** relaciona IP, hostname, identidad, hash, proceso y tiempo entre fuentes distintas.
- **Normalización:** hace comparables los formatos de dirección IP, nombres de host, usuarios y marcas temporales.

Ejemplo de correlación:

1. El SIEM detecta tráfico saliente inusual desde SERVIDOR-DB02.
2. NetFlow confirma un aumento de bytes hacia un destino externo.
3. El EDR revela un proceso no autorizado en el servidor.
4. Los logs de autenticación muestran uso de una cuenta administrativa fuera de horario.

La hipótesis de exfiltración gana fuerza porque varias fuentes independientes cuentan la misma historia.

## Dashboards

Un dashboard es una vista gráfica y centralizada de métricas, alertas y tendencias. En un SOC suele formar parte de una arquitectura de single pane of glass: un punto de inicio para observar la postura de seguridad.

Un dashboard puede mostrar:

- Eventos destacables por categoría: endpoint, red, identidad, acceso o amenaza.
- Alertas por criticidad: informativa, baja, media, alta o crítica.
- Evolución temporal de incidentes.
- Activos con mayor número de eventos.
- Resultados de escaneos de vulnerabilidades.
- Infecciones detectadas por antivirus o EDR.
- Picos de tráfico entrante o saliente.

Un pico de eventos de endpoint desde una línea base de 100 hasta 1.000 no confirma automáticamente un ataque. Es una señal para profundizar: identifica el host afectado, revisa los eventos crudos, compara con cambios aprobados y busca procesos o conexiones asociadas.

> El dashboard sirve para detectar dónde mirar; los registros subyacentes explican qué pasó.

## Informes automatizados

Los antivirus, EDR, SIEM y plataformas de orquestación pueden generar informes periódicos o por evento. Suelen incluir:

- ID del informe.
- Fecha de generación y periodo cubierto.
- Sistema o automatización que lo elaboró.
- Resumen ejecutivo.
- Severidad y descripción de cada hallazgo.
- Usuario, host, IP, archivo o proceso involucrado.
- Acciones automáticas ejecutadas.
- Recomendaciones, anexos, IoC y fragmentos de log.

### Cómo interpretarlos

Un informe que indique accesos masivos y rápidos a archivos, especialmente fuera del horario normal, puede coincidir con comportamiento de ransomware. Si el sistema suspendió la cuenta, aisló el equipo y activó el respaldo, revisa que esas acciones se hayan aplicado correctamente, preserva evidencia y determina el alcance.

Muchos fallos de inicio de sesión de administrador desde una IP interna pueden indicar:

- Una estación interna comprometida.
- Uso indebido de credenciales.
- Una configuración incorrecta.
- Una amenaza interna.

No concluyas que es necesariamente una amenaza interna: verifica el propietario del activo, procesos que lo ejecutaban, cambios recientes y si después hubo un inicio de sesión exitoso.

El tráfico saliente elevado desde una base de datos puede ser exfiltración, pero también una copia de seguridad autorizada. Contrástalo con el calendario de backups, la identidad usada, el destino permitido, la ventana de mantenimiento y el contenido disponible.

La instalación de software no autorizado o con hash no reconocido puede ser una infracción de política, un error del usuario o una cuenta comprometida. Confirmar con el usuario y correlacionar con autenticación y EDR evita una conclusión precipitada.

## Escáneres de vulnerabilidades

Un escaneo de vulnerabilidades identifica configuraciones, servicios o versiones potencialmente expuestas. Es una fuente esencial para priorizar la remediación, pero no prueba que alguien haya explotado el fallo.

Un informe típico incluye:

- Alcance, fecha y hora del escaneo.
- Herramienta, plugins, definiciones y método usado.
- Hosts, servicios, puertos, software y versiones afectados.
- Identificador de hallazgo, como un CVE.
- Evidencia detectada por el escáner.
- Severidad o puntuación CVSS.
- Impacto, recomendación y posible solución.

### CVE y CVSS

- **CVE:** identificador público de una vulnerabilidad conocida.
- **CVSS:** puntuación estándar de severidad técnica, normalmente de 0 a 10.

CVSS no es el riesgo completo para tu organización. También debes evaluar exposición a Internet, facilidad de explotación, explotación activa, importancia del activo, datos procesados, controles compensatorios y efecto operativo.

### Proceso correcto

1. Valida el hallazgo: puede ser un falso positivo, no aplicable al sistema o ya estar mitigado.
2. Confirma el activo, servicio, versión y evidencia.
3. Prioriza según riesgo técnico y contexto de negocio.
4. Aplica el parche o una mitigación aprobada.
5. Vuelve a escanear para verificar la remediación.

Si decenas de sistemas carecen de un mismo parche antiguo, el hallazgo apunta a un problema sistémico de gestión de parches, no solo a una incidencia de un host.

Cuando no es posible actualizar de inmediato, los controles compensatorios pueden incluir segmentación, restricción de acceso, deshabilitar un servicio no necesario, filtrado en firewall, monitorización reforzada o controles de aplicación. Consulta siempre el aviso actual del fabricante antes de aplicar una corrección concreta.

## Logs y centralización

Un log registra eventos de un sistema, aplicación o dispositivo. Entre las clases más importantes están:

- **Logs de red:** routers, switches, VPN, firewalls y flujos.
- **Logs de sistema:** arranque, servicios, errores y actividad del host.
- **Logs de aplicación:** acciones, errores, cambios y transacciones de una aplicación.
- **Logs de seguridad y autenticación:** inicios de sesión, privilegios, bloqueos y auditoría.
- **Logs web o proxy:** URLs, métodos HTTP, respuestas y destinos consultados.
- **Logs DNS:** consultas, respuestas y dominios solicitados.
- **Dumps de memoria:** estado capturado tras un fallo o para análisis forense.
- **Logs VoIP:** señalización y metadatos de llamadas; las grabaciones están sujetas a política y requisitos legales.

Syslog y sus implementaciones, como rsyslog o syslog-ng, permiten centralizar eventos de muchos sistemas. journalctl es la utilidad habitual para consultar el journal de systemd en Linux. Agentes de recolección multiplataforma, como NXLog, pueden enviar eventos de varios sistemas operativos a un SIEM.

La centralización protege la disponibilidad de la evidencia: un atacante que compromete un endpoint puede alterar sus logs locales, pero tendrá más difícil borrar una copia enviada previamente a un repositorio protegido.

## Datos de flujo: NetFlow, sFlow e IPFIX

Estas tecnologías resumen comunicaciones de red y ayudan a detectar consumo de ancho de banda, conexiones anómalas y posibles exfiltraciones.

### NetFlow

NetFlow recoge información de flujos IP, como origen, destino, puertos, protocolo, duración, paquetes y bytes. Es útil para responder:

- ¿Qué host transmite más datos?
- ¿Cuándo se produjo el aumento de tráfico?
- ¿Hacia qué destino se envió?
- ¿Qué protocolo y puertos se usaron?

No es una captura completa de paquetes: normalmente no muestra el contenido exacto del archivo transferido.

### sFlow

sFlow, Sampled Flow, usa muestras de paquetes y contadores de interfaz. Reduce el volumen de datos y ofrece visibilidad estadística, pero puede omitir un evento pequeño porque no todos los paquetes se capturan.

### IPFIX

IPFIX, Internet Protocol Flow Information Export, es un estándar para exportar información de flujos desde routers, sondas y otros dispositivos hacia colectores. Se utiliza en monitorización, gestión y, en algunos entornos, medición o facturación.

### Patrón de posible exfiltración

Un gran pico de tráfico saliente debe investigarse, no clasificarse de inmediato como una brecha. Busca el host emisor, destino, volumen, horario, usuario, proceso y actividad aprobada. Una copia de seguridad puede parecerse a una exfiltración si solo observas los bytes.

## Capturas de paquetes

Una captura de paquetes, PCAP, ofrece detalle de paquetes individuales: marcas temporales, IP de origen y destino, puertos, protocolo, flags TCP, tamaño y, según la captura y el cifrado, contenido.

NetFlow dice de forma resumida que hubo una comunicación; una PCAP puede ayudar a explicar cómo se produjo.

### Patrones frecuentes

| Patrón observado | Interpretación probable |
|---|---|
| Una IP de origen consulta muchos puertos del mismo destino | Escaneo de puertos o reconocimiento |
| Gran volumen de SYN hacia un destino desde una sola fuente, sin completar conexiones | Posible SYN flood o DoS |
| Gran volumen de SYN hacia un mismo destino desde muchas fuentes | Posible DDoS, a menudo asociado a botnet |
| Múltiples conexiones repetidas a un destino externo desconocido | Posible C2; correlacionar con DNS y EDR |

Un SYN flood intenta agotar la capacidad del destino con conexiones medio abiertas. La diferencia que más suele preguntar el examen es:

- **DoS:** el ataque procede principalmente de una fuente.
- **DDoS:** varias fuentes atacan al mismo objetivo.

En producción, unas pocas líneas no bastan para atribuir un DDoS con certeza: analiza tasas, duración, línea base y telemetría adicional. En el examen, identifica la característica más evidente del fragmento.

## Logs de firewall y WAF

### Firewall de red

Un firewall de capa 3 o 4 suele registrar:

- Fecha y hora.
- IP de origen y destino.
- Puerto de origen y destino.
- Protocolo.
- Acción: permitir, denegar o bloquear.

Una misma IP de origen que prueba puertos 22, 80, 443, 8080 y otros contra el mismo host está realizando probablemente un **escaneo de puertos**. La acción bloqueada indica que el intento fue mitigado por ese control, no que el atacante accedió al servicio.

Los intentos bloqueados siguen siendo útiles para identificar reconocimiento, campañas repetidas, origen de ataques o necesidad de endurecer reglas, pero suelen tener menor prioridad que una actividad equivalente permitida y con impacto.

### Web Application Firewall

Un WAF opera en capa 7 y puede inspeccionar peticiones HTTP. En sus registros pueden aparecer:

- Método HTTP, como GET o POST.
- URI y parámetros.
- Regla activada.
- Acción del WAF.
- Código de estado HTTP.
- IP de cliente y servidor web.

Una petición con patrones de sintaxis SQL, comparaciones lógicas siempre verdaderas, palabras como SELECT o DROP, o comentarios de SQL en un parámetro puede señalar una **inyección SQL**.

~~~text
GET /producto?id=42                 -> petición normal
GET /producto?id=[patrón SQL]       -> intento sospechoso; el WAF devuelve 403
~~~

Un código 2xx suele indicar éxito y un 403 suele indicar que el recurso o la petición fue prohibida, pero interpreta el código junto con la acción registrada por el WAF. La protección adecuada es defensa en profundidad:

- Consultas parametrizadas o sentencias preparadas.
- Validación y sanitización de entradas.
- Privilegios mínimos para la cuenta de base de datos.
- Manejo seguro de errores.
- Reglas WAF actualizadas.

El WAF puede bloquear el intento; el desarrollo seguro elimina la causa vulnerable.

## Logs de aplicación

Los logs de aplicación muestran lo que ocurre dentro de un programa. Un formato común incluye fecha, hora, ID de evento, descripción, usuario, acción y detalles.

En un procesador de textos, abrir, guardar o imprimir documentos puede ser normal. Un patrón como este exige atención:

1. Un usuario abre un documento.
2. La aplicación detecta un intento de ejecutar una macro.
3. La política bloquea la macro.
4. El escáner identifica coincidencia con malware conocido.
5. El archivo queda en cuarentena y se alerta al administrador.

La conclusión sería que el archivo con la macro es sospechoso o malicioso, aunque el control haya evitado su ejecución. Conserva el artefacto de forma segura, identifica el origen —por ejemplo, un correo— y busca el mismo hash o nombre en el resto de los endpoints.

> Lee la secuencia completa: la relación entre eventos proporciona más contexto que una línea aislada.

## Logs de endpoint: antivirus y EDR

Un endpoint detection and response puede registrar descargas, ejecución de archivos, árboles de procesos, hashes, cambios de registro, conexiones salientes, desactivación de defensas y acciones de contención.

Una cadena de compromiso típica puede ser:

1. El usuario descarga un ejecutable desde el navegador.
2. El antivirus lo marca como sospechoso.
3. El usuario ignora o anula la advertencia.
4. El proceso descarga una segunda carga.
5. Aparece un proceso nuevo y desconocido.
6. Se modifica el registro u otro mecanismo de persistencia.
7. Se observan conexiones salientes inusuales.
8. Se genera una alerta de posible exfiltración.

Esta secuencia apoya la hipótesis de malware con descarga por etapas, persistencia y posible comunicación con infraestructura externa. La prioridad es contener el endpoint conforme al procedimiento, conservar evidencia, evaluar alcance, revisar cuentas y determinar qué datos pudieron salir.

Un hash es un IoC muy específico para identificar una muestra conocida, pero no basta como único indicador: un atacante puede modificar un archivo y cambiar su hash. Combina hash, comportamiento, proceso padre-hijo, usuario, ruta y destino de red.

## Logs de seguridad del sistema operativo

Los logs específicos del sistema operativo suelen registrar inicios de sesión correctos y fallidos, bloqueos de cuenta, privilegios, ejecución de servicios y cambios relevantes. Para analizar intentos de contraseña, observa:

- Cuenta objetivo.
- IP o equipo de origen.
- Frecuencia y periodo.
- Número de cuentas afectadas.
- Patrón de contraseñas, si el escenario de examen lo muestra.
- Presencia de inicio de sesión exitoso después de varios fallos.

| Patrón | Ataque probable |
|---|---|
| Intentos sistemáticos, secuenciales o aparentemente aleatorios contra una cuenta | Fuerza bruta |
| Palabras comunes y variantes previsibles contra una cuenta | Ataque de diccionario |
| Una misma contraseña contra muchas cuentas | Password spraying |
| Pares de usuario y contraseña reutilizados en muchas cuentas | Credential stuffing |

Los sistemas reales no suelen guardar contraseñas en claro en los logs. Si el examen enseña candidatos, úsalo para reconocer el patrón; no asumas que este nivel de detalle estará disponible en producción.

El bloqueo de cuenta limita intentos, pero no demuestra que no exista compromiso. Un inicio de sesión exitoso anómalo después de fallos repetidos debe elevar la prioridad.

## Logs y alertas de IDS/IPS

- **IDS, Intrusion Detection System:** detecta y alerta sobre actividad sospechosa; normalmente no la bloquea.
- **IPS, Intrusion Prevention System:** puede detectar y bloquear actividad maliciosa al operar en línea.

La acción importa tanto como la severidad. Considera estos dos ejemplos:

| Evento | Acción | Prioridad inicial |
|---|---|---|
| Inyección SQL de gravedad alta | Bloqueado | Investigar campaña y origen, pero el control impidió ese intento |
| Exfiltración de datos de gravedad alta | Alertado, no bloqueado | Investigación inmediata por posible impacto real |

Al priorizar, pregúntate:

1. ¿La acción fue bloqueada, solo alertada o monitorizada?
2. ¿El ataque pudo afectar confidencialidad, integridad o disponibilidad?
3. ¿Hay evidencia de éxito o consecuencias?
4. ¿Es una actividad activa, recurrente o de alto impacto?

Un evento bloqueado no debe ignorarse; puede indicar que alguien está realizando reconocimiento o apuntando a un activo concreto. Sin embargo, un posible robo de datos no bloqueado normalmente exige atención antes.

## Logs de red y ARP spoofing

Los routers y switches registran interfaces, acción, IP de origen y destino, puertos, protocolos, respuestas ARP y cambios de estado.

Una respuesta ARP relaciona una dirección IP con una dirección MAC. El siguiente patrón resulta sospechoso:

~~~text
192.168.1.10 está en MAC-A
192.168.1.10 está en MAC-B pocos segundos después
192.168.1.10 vuelve a MAC-A y luego a MAC-B
~~~

La asociación repetida de la misma IP con MAC distintas puede indicar **ARP spoofing** o ARP poisoning, que se usa a menudo para desviar tráfico y realizar un ataque man-in-the-middle.

Antes de concluirlo, correlaciona con DHCP, tablas ARP de otros equipos, puerto del switch, cambios autorizados, alta disponibilidad, virtualización y aleatorización de MAC. La inconsistencia es un indicador, no una prueba aislada.

Las conexiones DNS por UDP 53, HTTPS por TCP 443, SSH por TCP 22 o ICMP pueden ser totalmente normales. El contexto define la sospecha: frecuencia, dirección, volumen, horario, host, dominio y comportamiento previo.

## Metadatos

Los metadatos son datos sobre otros datos. Aportan contexto sin mostrar necesariamente el contenido del objeto.

En un archivo, pueden incluir:

- Nombre, tamaño y extensión.
- Tipo real, MIME o firma de archivo.
- Ruta.
- Fechas de creación, modificación y último acceso.
- Propietario, permisos y autor.
- Hash o checksum.
- Dispositivo, ubicación o aplicación de origen.

En un correo pueden incluir remitente, destinatarios, fecha, asunto, Message-ID y ruta de servidores transitados. En llamadas o actividad móvil, pueden incluir hora, duración, identificadores y volumen, siempre conforme a políticas y requisitos legales.

### Ejemplos de análisis

| Hallazgo de metadatos | Qué puede indicar | Verificación necesaria |
|---|---|---|
| Archivo llamado factura.pdf cuyo tipo real es ejecutable | Ocultación mediante extensión engañosa | Revisar firma, MIME, cabecera y origen |
| Archivo descargado en una ruta temporal inesperada | Posible ejecución o staging de malware | Correlacionar con EDR, usuario y proceso |
| Fechas incompatibles con el contexto | Posible manipulación o archivo reutilizado | Comparar con correo, logs y sistema de archivos |
| Hash conocido como malicioso | IoC fuerte para esa muestra | Buscar alcance y validar la inteligencia de amenazas |
| Propietario del archivo | Posible punto de entrada o responsable del recurso | Entrevistar al usuario y revisar actividad asociada |

MD5 puede aparecer como checksum heredado, pero SHA-256 es preferible para identificar archivos en flujos de seguridad modernos. Ni el nombre, ni una fecha, ni una ruta o un hash aislado sustituyen al análisis contextual.

## Patrones que debes reconocer inmediatamente

| Evidencia | Respuesta esperada |
|---|---|
| Una fuente prueba muchos puertos de un host | Escaneo de puertos |
| Muchos SYN desde una fuente al mismo destino | Posible DoS por SYN flood |
| Muchos SYN desde diversas fuentes al mismo destino | Posible DDoS |
| Parámetros web con sintaxis SQL inusual | Intento de inyección SQL |
| Macro bloqueada y archivo enviado a cuarentena | Documento malicioso mitigado |
| Descarga, proceso desconocido, persistencia y tráfico saliente | Posible infección de endpoint y C2/exfiltración |
| Intentos de contraseña secuenciales o aleatorios | Fuerza bruta |
| Intentos basados en palabras comunes | Ataque de diccionario |
| Mismo IP con distintas MAC repetidamente | Posible ARP spoofing |
| Gran tráfico saliente desde un activo sensible | Posible exfiltración; descartar backup u operación autorizada |
| Vulnerabilidad crítica en un escáner | Riesgo que requiere validación y remediación, no prueba de explotación |
| Alerta IPS bloqueada | Intento mitigado; conservar y correlacionar |
| Alerta IDS/IPS no bloqueada de posible exfiltración | Prioridad alta: evaluar éxito, alcance y datos afectados |

## Errores comunes

- Tratar toda alerta como un incidente confirmado.
- Ignorar una alerta de baja severidad que, combinada con otras, revela un ataque.
- Elegir la vulnerabilidad con CVSS más alto sin valorar exposición y criticidad del activo.
- Confundir datos de flujo con una captura de paquetes completa.
- Asumir que un evento bloqueado no merece registro ni análisis.
- Suponer que tráfico elevado equivale automáticamente a exfiltración.
- Concluir ARP spoofing sin descartar cambios legítimos de red.
- Investigar datos sin normalizar zona horaria, hostnames o identidades.
- Aplicar una acción técnica sin preservar evidencia ni comprobar el alcance.

## Lista final para el examen

Ante cualquier registro, piensa:

- ¿Qué fuente es y qué visibilidad ofrece?
- ¿Qué activo, usuario, origen, destino y momento aparecen?
- ¿Cuál es el patrón repetido o anómalo?
- ¿Fue permitido, bloqueado, detectado o cuarentenado?
- ¿Hay impacto confirmado o solo un intento?
- ¿Qué otra fuente lo confirmaría?
- ¿Cuál es la acción más directa y proporcionada?

El objetivo 4.9 evalúa razonamiento basado en evidencia. Lee el contexto, relaciona las fuentes y prioriza el impacto real sobre etiquetas aisladas de severidad.
