# 4.5 Capacidades de seguridad empresarial

## Objetivo del examen

**Dado un escenario, modificar las capacidades de una organización para mejorar su seguridad.**

El objetivo no consiste en memorizar pantallas de administración de un producto. Debes reconocer el riesgo descrito, elegir el control adecuado, configurarlo con el alcance correcto y comprobar que no rompe una función de negocio.

Una capacidad empresarial combina personas, procesos y tecnología. Instalar EDR, por ejemplo, no basta: se debe decidir qué eventos recoge, qué alertas se priorizan, quién puede aislar un equipo y cómo se revierte una contención errónea.

## Método para resolver escenarios

1. Identifica el activo, dato y flujo que se debe proteger.
2. Define la amenaza: malware, exfiltración, suplantación, acceso no autorizado o indisponibilidad.
3. Aplica mínimo privilegio: permite solo usuarios, dispositivos, puertos, protocolos y acciones necesarios.
4. Combina controles preventivos, detectivos y de respuesta.
5. Delimita el alcance: grupo, unidad organizativa, red, aplicación, rol, ubicación o canal.
6. Prueba con datos sintéticos y un grupo piloto.
7. Monitoriza efectos, falsos positivos, disponibilidad y evasiones; ajusta y documenta.

> Una coincidencia de una regla o una anomalía no prueba por sí sola que exista un incidente. La respuesta debe ser proporcional al riesgo: registrar, alertar, advertir, restringir o bloquear.

## Cambio seguro y línea base

Todo cambio relevante debe tener propietario, justificación, alcance, fecha de revisión, plan de despliegue y reversión. Prueba primero en laboratorio o anillo piloto, comunica el cambio y supervisa el resultado.

Una **línea base segura** es una configuración aprobada y documentada que sirve para desplegar, comparar y restaurar sistemas. El endurecimiento incluye:

- Cambiar credenciales y configuraciones predeterminadas.
- Desactivar servicios, cuentas, puertos y software innecesarios.
- Aplicar actualizaciones y parches tras pruebas.
- Activar registros, sincronización horaria, cifrado y EDR/antimalware.
- Sustituir o aislar software sin soporte.
- Revisar desviaciones respecto de la línea base.

Una línea base no es inmutable: debe actualizarse mediante control de cambios cuando una modificación legítima altere archivos, configuraciones o servicios.

### Restricción de aplicaciones

La **lista de permitidos** permite ejecutar únicamente software aprobado. Es más sólida que intentar bloquear todo el malware conocido.

La **lista de bloqueo** deniega aplicaciones, hashes, editores o rutas concretas. Es útil ante una amenaza conocida, pero no protege por sí sola frente a malware nuevo.

| Criterio | Uso | Precaución |
|---|---|---|
| Editor o firma | Permitir software de proveedores aprobados | Una firma válida no sustituye parches |
| Ruta | Bloquear ejecución desde carpetas temporales o de descargas | Una ruta confiable mal protegida puede ser abusada |
| Hash | Bloquear un archivo malicioso conocido | El hash cambia con una nueva versión |
| Paquete | Gestionar aplicaciones instaladas | Revisar dependencias y versiones |

Ejemplo: si los usuarios ejecutan adjuntos maliciosos desde directorios temporales, una regla de ruta puede impedir esa ejecución, manteniendo excepciones mínimas y probadas.

### GPO, SELinux y AppArmor

Las **GPO** permiten aplicar centralmente configuraciones Windows: políticas de contraseña, bloqueo de cuentas, firewall, restricciones de software y líneas base. Vincúlalas al grupo o unidad organizativa correctos, prueba herencia y precedencia, y conserva un plan de reversión.

En Linux, los permisos habituales usan **DAC** (*Discretionary Access Control*), donde el propietario puede modificar permisos. **SELinux** y **AppArmor** añaden **MAC** (*Mandatory Access Control*), restringiendo lo que un proceso puede hacer incluso si DAC lo permite.

| Modo SELinux | Efecto |
|---|---|
| Disabled | No aplica la política; se pierde esta capa |
| Permissive | Registra violaciones, pero no las bloquea; útil temporalmente para ajuste |
| Enforcing | Aplica y bloquea acciones no permitidas |

Ante un fallo de compatibilidad, revisa registros y corrige políticas o contextos. No desactives permanentemente SELinux como solución rápida.

## Firewalls, ACL y segmentación

Un firewall controla tráfico según dirección, origen, destino, zona, protocolo, puerto, estado de conexión, aplicación o identidad. Sus acciones pueden permitir, denegar, registrar, limitar o redirigir.

### Reglas y ACL

Las ACL suelen evaluarse de arriba abajo. La primera regla que coincide determina la acción.

- Coloca reglas específicas antes de reglas generales.
- Restringe origen, destino, protocolo y puerto tanto como sea posible.
- Registra permisos de alto riesgo y denegaciones relevantes.
- Aplica denegación predeterminada o una regla final equivalente cuando el diseño lo permita.
- Revisa reglas amplias, temporales, sin propietario o sin fecha de expiración.

Abrir un puerto de forma segura significa permitir una comunicación concreta entre un origen autorizado y un servicio necesario; no permitir todo el tráfico hacia un servidor.

### Tráfico entrante, saliente y reenvío

- **Entrante:** protege servicios publicados. Expón solo los necesarios, preferiblemente en una DMZ.
- **Saliente:** reduce malware y exfiltración. No se debe asumir que todo tráfico de salida es legítimo.
- **Port forwarding:** dirige tráfico entrante a un host interno; aumenta exposición y debe limitarse y registrarse.

Los firewalls de host protegen cada endpoint; los de red protegen segmentos completos. Usar ambos aporta defensa en profundidad.

### Zonas y segmentación

Separa activos con diferente sensibilidad: Internet, DMZ, usuarios, servidores, bases de datos, administración, invitados, IoT y cuarentena. El tráfico entre zonas debe atravesar controles explícitos.

Un servidor web público puede aceptar HTTPS desde Internet, pero no debería tener acceso directo e ilimitado a una base de datos interna.

### Inline, pasivo y fallo

| Diseño | Ventaja | Riesgo o uso |
|---|---|---|
| En línea (*inline*) | Puede bloquear o modificar tráfico | Un fallo puede afectar disponibilidad |
| Pasivo, TAP o monitor | Observa sin estar en el flujo | Detecta, pero no bloquea directamente |
| Fail-open | Mantiene conectividad si el control falla | Puede permitir tráfico no inspeccionado |
| Fail-closed | Mantiene bloqueo si el control falla | Puede interrumpir el servicio |

La elección depende del riesgo y de los requisitos de disponibilidad; la alta disponibilidad puede reducir el conflicto entre seguridad y continuidad.

### Controles de red

- **WAF:** protege aplicaciones web y entiende solicitudes HTTP/S.
- **NGFW:** añade inspección de aplicaciones, identidad e IPS a las capacidades de firewall.
- **UTM:** integra funciones como firewall, antimalware, filtrado web e IPS.
- **Proxy/SWG:** intermedia el acceso web, aplica política y registra.
- **IDS:** detecta y alerta, normalmente de forma pasiva.
- **IPS:** suele estar en línea y puede bloquear.

Si el escenario exige detener una intrusión, selecciona IPS o una regla de bloqueo. Si exige observar sin arriesgar disponibilidad, selecciona un IDS o sensor pasivo.

## Protocolos, puertos y transporte

Un puerto es un extremo lógico de comunicación; un protocolo define cómo se intercambian los datos. Usa versiones que aporten cifrado, autenticación e integridad.

| Necesidad | Evitar cuando sea posible | Preferir |
|---|---|---|
| Navegación web | HTTP | HTTPS con TLS |
| Administración de consola | Telnet | SSH |
| Transferencia de archivos | FTP | SFTP o FTPS |
| Directorio | LDAP sin protección | LDAPS o LDAP con TLS |
| Lectura de correo | POP3/IMAP sin TLS | POP3S/IMAPS o TLS configurado correctamente |
| Envío de correo | SMTP sin protección | SMTP autenticado con TLS |
| Gestión de red | SNMP antiguo | SNMPv3 |
| Registro remoto | Syslog no protegido | Transporte protegido, como Syslog sobre TLS |

Para cada puerto permitido, documenta servicio, propietario, origen, destino, protocolo, justificación y fecha de revisión. Abre solo lo necesario y bloquea el resto.

Cambiar un servicio a un puerto no estándar solo añade oscuridad. No sustituye cifrado, parcheado, autenticación fuerte ni filtrado.

**TCP** es orientado a conexión, con confirmación, orden y retransmisión; se usa cuando la entrega e integridad son prioritarias. **UDP** tiene menos sobrecarga y favorece baja latencia, con pérdida tolerable. TCP no es automáticamente seguro ni UDP automáticamente inseguro: la seguridad depende de los controles de la capa adecuada.

## Control de acceso a la red (NAC)

**NAC** (*Network Access Control*) evalúa un endpoint antes de conceder acceso y puede reevaluarlo durante la conexión. Comprueba identidad, postura del equipo y contexto.

Factores frecuentes:

- Identidad de usuario y dispositivo.
- Certificado, MFA o autenticación EAP.
- Parches, EDR/antivirus, cifrado de disco y configuración.
- Rol, tipo de dispositivo, ubicación, horario y nivel de riesgo.

Flujo habitual:

1. El endpoint solicita conexión.
2. NAC autentica y evalúa postura.
3. Si cumple, concede el acceso mínimo correspondiente.
4. Si falla, deniega o lo dirige a una red de cuarentena/remediación.
5. Allí solo puede actualizarse o usar los servicios necesarios.
6. Tras corregirse, NAC reevalúa y concede acceso.

La red de cuarentena no debe permitir movimiento lateral hacia recursos internos.

### 802.1X, EAP y RADIUS

**802.1X** controla acceso por puerto. Intervienen:

- **Supplicant:** cliente que solicita acceso.
- **Authenticator:** switch o punto de acceso que controla el puerto.
- **Authentication server:** servidor que valida identidad, habitualmente RADIUS.

**EAP** transporta métodos de autenticación. Esta arquitectura ayuda a impedir que un dispositivo no autorizado acceda solo por conectarse al cable o Wi-Fi.

| Modalidad NAC | Adecuada para | Consideración |
|---|---|---|
| Agente persistente | Equipos corporativos gestionados | Mayor comprobación continua; requiere gestión |
| Agente no persistente/portal cautivo | Invitados, BYOD, campus | Menor control y posibles incompatibilidades |
| Sin agente | IoT o equipos no administrables | Requiere perfilado y segmentación adicional |

NAC adaptativo puede usar rol, ubicación, hora o riesgo. Un inicio desde ubicación inusual puede requerir MFA o acceso limitado, pero no prueba por sí solo una intrusión.

### Wi-Fi empresarial

Para entornos corporativos se prefiere WPA3-Enterprise con 802.1X y RADIUS, junto con segmentación de empleados, invitados, IoT y administración. También se revisan firmware de puntos de acceso, aislamiento de invitados y mecanismos heredados como WPS.

## Prevención de pérdida de datos (DLP)

**DLP** (*Data Loss Prevention*) identifica datos sensibles y aplica una política cuando se intentan enviar, compartir, copiar, imprimir, descargar, subir o usar en un canal no autorizado.

### Diseño de una regla

1. Define el dato: información regulada, financiera, sanitaria, secretos comerciales o propiedad intelectual.
2. Define alcance: toda la organización, grupo, unidad organizativa, rol o proyecto.
3. Define canal: correo, chat, almacenamiento cloud, endpoint, navegador o aplicación.
4. Elige detección: tipo predefinido, expresión regular, cadena, lista de palabras, clasificación o huella documental.
5. Ajusta confianza, contexto y número mínimo de coincidencias.
6. Define acción y destinatarios de alertas.

Los motores DLP pueden utilizar **OCR** para localizar texto sensible en imágenes o documentos escaneados. Así se reduce la evasión mediante capturas o fotografías.

### Umbrales y acciones

Una secuencia de caracteres puede parecer sensible por su formato, pero el contexto cercano incrementa o reduce la confianza.

- Umbral bajo: más detección, más falsos positivos.
- Umbral alto: menos ruido, con riesgo de pasar por alto algunas filtraciones.
- Mínimo de coincidencias: evita acciones severas por una detección aislada poco fiable.

| Acción | Uso apropiado |
|---|---|
| Auditar | Fase inicial o riesgo bajo |
| Alertar | Requiere análisis del SOC o propietario |
| Advertir | Error probable que el usuario puede corregir |
| Solicitar justificación | Excepción de negocio con trazabilidad |
| Bloquear | Datos muy sensibles o canal prohibido |
| Cuarentenar | Correo o archivo que debe revisarse |
| Restringir compartir, copiar, imprimir o descargar | Repositorios que requieren colaboración controlada |
| Cifrar o redirigir | El envío es legítimo solo por un canal protegido |

Ejemplo: si un archivo regulado se comparte externamente, una política puede bloquear el compartir externo, informar al usuario y generar una alerta. No necesita bloquear necesariamente la colaboración interna.

### Pruebas DLP

Prueba con información sintética, variaciones de formato, adjuntos e imágenes. Verifica detección, excepciones con caducidad, entrega de alertas y mensajes útiles para el usuario. Es habitual comenzar en auditoría y pasar progresivamente a advertencia o bloqueo tras ajustar falsos positivos y negativos.

## Filtrado web y DNS

El filtrado reduce acceso a phishing, malware, contenido inapropiado y servicios no autorizados.

### Filtrado web

Puede aplicarse mediante agente de endpoint, proxy centralizado, firewall/SWG o servicio cloud. Sus técnicas incluyen:

- Escaneo de URL e inteligencia de amenazas.
- Reputación de dominio o sitio.
- Categorías de contenido.
- Listas explícitas de permitir o bloquear.
- Análisis de descargas y adjuntos.

Un agente protege también a usuarios remotos. Un proxy central facilita aplicación uniforme y registro del tráfico que atraviesa.

### Filtrado DNS

El filtrado DNS bloquea la resolución de dominios prohibidos o maliciosos: el resolutor no entrega la dirección IP solicitada.

Es eficiente para cortar dominios maliciosos, pero no inspecciona por sí mismo el contenido web ni protege frente a acceso directo por IP. Debe acompañarse de DNS corporativo forzado, controles de salida y otras capas.

Mantén excepciones controladas: bloquear una categoría completa puede afectar a equipos de marketing, soporte, investigación o formación.

## Seguridad de correo

El correo es un vector común de suplantación, phishing, malware y exfiltración. Combina autenticación de dominio, gateway, filtrado y DLP.

| Control | Qué valida | Idea clave |
|---|---|---|
| SPF | Servidores/IP autorizados a enviar por un dominio | Reduce falsificación de remitente |
| DKIM | Firma criptográfica de partes del mensaje y cabeceras | Ayuda a comprobar origen firmado e integridad |
| DMARC | Alineación de dominio y política basada en SPF y/o DKIM, más informes | Indica cómo tratar fallos |

Despliega DMARC gradualmente: primero monitoriza informes, corrige emisores legítimos y alineación, después aplica cuarentena y finalmente rechazo si procede. Rechazar sin inventario de todos los emisores puede bloquear correo válido.

Un **email gateway** es el punto de entrada y salida de mensajes. Puede enrutar, detectar spam/phishing/malware, analizar enlaces y adjuntos, aplicar DLP al correo saliente, cuarentenar, rechazar y cifrar mensajes.

Los filtros antispam pueden usar contenido, reputación, reglas, listas de bloqueo y análisis estadístico. Las cuarentenas y falsos positivos deben revisarse.

## EDR, FIM, XDR, UBA y UEBA

### EDR

**EDR** (*Endpoint Detection and Response*) recoge telemetría de endpoints: procesos, cambios de registro, conexiones, comandos, archivos y otros eventos. Centraliza esos datos para detectar, investigar y responder.

Puede alertar, aislar un equipo, detener procesos, cuarentenar archivos, recoger evidencia forense o ejecutar respuestas aprobadas. La automatización reduce el tiempo de contención, pero acciones de alto impacto requieren políticas claras y posibilidad de reversión.

### FIM

**FIM** (*File Integrity Monitoring*) compara archivos críticos con una línea base conocida como buena, normalmente mediante hashes y metadatos. Detecta modificaciones no autorizadas en binarios, configuraciones o archivos del sistema.

La línea base debe crearse desde un sistema confiable y actualizarse tras cambios aprobados; de lo contrario, actualizaciones legítimas causarán alertas repetidas.

### XDR

**XDR** (*Extended Detection and Response*) correlaciona telemetría de endpoints, identidad, correo, red, servidores y cloud. Aporta más contexto que un EDR centrado principalmente en endpoints y acelera la investigación de cadenas de ataque.

### UBA y UEBA

**UBA** aprende el comportamiento normal de usuarios; **UEBA** también considera entidades como hosts, routers, aplicaciones y cuentas de servicio.

Puede alertar por inicios de sesión inusuales, accesos ajenos al rol, transferencias anómalas, escalada de privilegios o cambios bruscos en cuentas de servicio. Una alerta requiere contexto: viaje, cambio de puesto o proyecto urgente pueden ser explicaciones legítimas.

## SD-WAN y SASE

**SD-WAN** centraliza políticas de conectividad WAN y selecciona rutas entre enlaces según rendimiento, coste o disponibilidad. Ayuda a aplicar políticas coherentes entre sedes.

**SASE** integra conectividad y controles de seguridad entregados desde cloud; puede combinar SD-WAN, firewall, secure web gateway, CASB y ZTNA. Es útil para organizaciones distribuidas, pero requiere definir identidad, acceso mínimo, segmentación, registros, residencia de datos y continuidad del proveedor.

## Guía rápida por escenario

| Situación | Modificación principal | Controles complementarios |
|---|---|---|
| Administración remota en texto claro | Sustituir Telnet por SSH y limitar redes de administración | MFA, ACL, bastión, registros |
| Servicio web solo debe ser seguro | Permitir HTTPS y retirar HTTP cuando sea viable | TLS válido, WAF, parches |
| Portátil sin parches intenta conectarse | NAC con remediación/cuarentena | 802.1X, EDR, VLAN aislada |
| BYOD requiere Internet, no recursos internos | Red de invitados segmentada | NAC/portal, filtrado DNS/web |
| Datos sensibles salen por correo o cloud | DLP por clasificación y canal | Gateway, cifrado, alertas SOC |
| Phishing que suplanta el dominio | SPF, DKIM y DMARC gradual | Gateway, antiphishing, informes DMARC |
| Usuario abre enlaces maliciosos | Filtrado web/DNS por reputación y categorías | Proxy/SWG, EDR, registros |
| Endpoint con comportamiento sospechoso | Aislar con EDR e investigar | FIM, XDR/SIEM, restaurar línea base |
| Cuenta accede a datos ajenos a su función | Alertar con UEBA y aplicar mínimo privilegio | Revisión de roles, MFA, DLP |
| Aplicación Linux excede su función | Ajustar SELinux/AppArmor | Parches, segmentación, registros |
| ACL demasiado amplia | Restringir origen, destino, protocolo y puerto | Orden correcto, caducidad, logging |

## Errores comunes

- Confundir DLP con cifrado: DLP controla uso o salida; cifrado protege el contenido.
- Creer que un puerto no estándar protege un servicio vulnerable.
- Aplicar una regla global cuando el escenario exige un grupo o canal concreto.
- Activar bloqueo sin ajustar umbrales ni medir falsos positivos.
- Confundir IDS con IPS: IDS detecta; IPS puede bloquear.
- Confundir EDR con XDR: EDR se centra en endpoints; XDR correlaciona varias capas.
- Creer que DNS filtering inspecciona toda la página web.
- Desactivar SELinux para resolver una incompatibilidad.
- Conceder acceso completo a un dispositivo que falló NAC.
- Configurar DMARC en rechazo sin identificar emisores legítimos.

## Autoevaluación

1. Un portátil sin parches se conecta por VPN. ¿Qué lo puede limitar a una red de actualización?
   - **NAC**, con cuarentena o remediación.

2. Se debe impedir compartir externamente documentos regulados, pero permitir colaboración interna. ¿Qué control corresponde?
   - Una regla **DLP** con clasificación, alcance de compartición externa y acción de bloqueo o advertencia.

3. Una ACL permite una regla general antes de una denegación específica. ¿Qué se revisa?
   - El **orden de ACL**: las reglas específicas van antes de las generales.

4. Un endpoint inicia procesos y conexiones anómalos. ¿Qué solución puede aislarlo y proporcionar evidencia?
   - **EDR**.

5. Un dominio se usa para enviar mensajes falsificados. ¿Qué combinación autoriza emisores, firma correo y publica una política?
   - **SPF, DKIM y DMARC**.

6. Un empleado descarga un volumen de datos fuera de su patrón habitual. ¿Qué capacidad detecta esa desviación?
   - **UBA/UEBA**; después se investiga antes de concluir que hay un incidente.
